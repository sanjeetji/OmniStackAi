# ADR-0001 — Modular monorepo and provider boundaries

Status: Accepted

## Problem

OmniStackAI needs one repository structure that can evolve with coordinated contracts while
avoiding premature service and provider lock-in.

## Decision

Use the Section 74 modular monorepo. The principal eventual deployable boundaries are
`control-plane`, `agent-engine`, and `runner-manager`. Directories under `modules/` remain
logical boundaries and do not become microservices without measured scaling, security, or
ownership evidence.

Platform/domain code will depend on platform-owned provider contracts for models, runtimes,
builds, devices, Git, databases, deployments, artifacts, signing, secrets, telemetry, and MCP
tools. PostgreSQL remains the non-negotiable control-plane database.

## Consequences

- Cross-module contract changes can remain atomic in one pull request.
- Provider adapters can change without contaminating core domain contracts.
- The repository contains placeholders only during R-001; implementation arrives through
  later Tracker IDs.
- A repository split requires benchmark evidence, an ADR, and a migration/exit strategy.

## Evidence and review trigger

Source: Implementation Brief Sections 25, 74, 75, 77, 91, and 92. Review only when measured
build time, access boundaries, independent release ownership, or scaling requirements justify
a different boundary.
