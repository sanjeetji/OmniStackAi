# R-431: Scope → Application IRs — materialize a multi-app ecosystem from one prompt

## Status
DONE (2026-09-13). Second brick of the differentiating spine. R-430's Ecosystem Scope
Compiler *proposes* a multi-app ecosystem; R-431 makes it *real*: it maps each proposed `AppSurface` to a
valid Application IR and materializes the chosen build scope as MULTIPLE owned Git repos from a single prompt
— the tangible "wow" (customer app + merchant portal + admin, each owned code).

## Objective
Add a Python-3.13-stdlib-only `intake/ecosystem.py` that turns a `ScopeProposal` (+ a chosen build-scope
option) into an `EcosystemPlan`: one framework-neutral, `validate_ir`-clean `ApplicationIR` per selected
surface, built from a curated per-domain data model + a deterministic CRUD deriver (standard LIST/GET/CREATE/
UPDATE/DELETE + sub-collection LIST_BY endpoints that WIRE to real repository-backed handlers — no stubs, no
fake data). Then `build_ecosystem(plan, out_dir)` materializes each app into its own owned Git repo under
`out_dir/<slug>/` by reusing the existing `build_app_from_ir` (assembler + git-service). Ship a deterministic
plan CLI (`task agent-engine:ecosystem:plan`) and an opt-in build CLI (`task agent-engine:ecosystem:build`).
Do NOT change the Application IR, adapters, assembler, Git-service, or DB engine (PostgreSQL stays); keep
`task verify` offline/deterministic (0 model calls); the classifier/planner are deterministic (any LLM
refinement stays an opt-in later brick).

## Requirements
- `intake/ecosystem.py` (stdlib + intra-package imports only): a curated `DOMAIN_ENTITIES` model (2–4 real
  entities with typed fields + FK relations) for each of the 10 `DOMAIN_LIBRARY` domains; a deterministic
  CRUD API/screen deriver that emits canonical shapes the generators wire (GET /<plural>, POST /<plural>,
  GET /<plural>/{id}, PUT /<plural>/{id}, DELETE /<plural>/{id}, and GET /<parents>/{id}/<children> for a
  child with exactly one FK relation); `surface_to_ir(proposal, surface) -> ApplicationIR` (name = surface,
  roles derived from the proposal actors, entities = the domain model, apis/screens derived, Next.js web +
  Python backend + PostgreSQL), normalized and `validate_ir`-clean.
- `SurfaceApp` (surface + ir), `EcosystemPlan` (prompt, domain, option_id, apps), and
  `plan_ecosystem(proposal, option_id="complete") -> EcosystemPlan` (respects the option's surface subset).
- `build_ecosystem(plan, out_dir, *, author_name, author_email) -> EcosystemBuildResult` — materialize each
  app via `build_app_from_ir` into `out_dir/<slug>/`; JSON-safe result (per-app name, slug, target_dir,
  file_count, commit_sha).
- Export the public API from `intake/__init__.py`; add a deterministic plan CLI `intake/ecosystem_plan.py`
  and an opt-in build CLI `intake/ecosystem_build.py`; wire `task agent-engine:ecosystem:plan` and
  `:build` (+ `scripts/agent-engine.sh` cases + usage).
- `tests/test_ecosystem.py`: every domain's data model + every surface IR passes `validate_ir` with no
  errors; `plan_ecosystem` app count matches the option's surfaces (Complete = all, Customer-only = customer
  surfaces); determinism/purity; derived CRUD wires (Op.LIST/GET/CREATE/UPDATE/DELETE present via
  `wire_endpoint`); one `build_ecosystem` into a temp dir produces the expected repos (like `test_build_app`).

- Demo (deterministic): `task agent-engine:ecosystem:plan -- "Create a food delivery app …"` → domain

  Dashboard), each 3 entities / 17 APIs / 6 screens. `task agent-engine:ecosystem:build -- "…"` materialized
  **4 owned Git repos** (164 files each, first commit authored sanjeetji) from one prompt.
- Every produced IR is `validate_ir`-clean; the derived CRUD wires to real repositories (Op.LIST/GET/CREATE/
  UPDATE/DELETE + sub-collection LIST_BY all resolve via `wire_endpoint` — no 501 stubs); plan is deterministic.
- Verified the generated ecosystem apps COMPILE clean: `tsc --noEmit` on all four food-delivery apps → **0
  errors**. Running that exposed 4 generator compile bugs (in FK / multi-subcollection / filterable-child
  paths that minimal-blog/rideshare never generate), all fixed in `codegen/nextjs.py`:
  - FK-relation `<select>` editor `onChange` emitted an over-braced arrow body (`=> {{`) — fixed to `=> {`.
  - the shared bool-badge helper closed its inline style with a single brace (`}>`) — fixed to `}}>`.
  - a parent list with 2+ sub-collections rendered the search-bar and filter-chips `<div>`s as two JSX
    roots inside one `{…&& ( )}` — wrapped them in a fragment (`<>…</>`).
  - the generated entity interface omitted the scalar `<relation>_id` FK column (only the hydrated relation
    object) that the DB schema, API params, and editor form-state use — now emitted for to-one relations.
- Regression: `tests/test_ecosystem.py` (9 tests) — per-domain valid IRs, option app-counts, deterministic
  plan, CRUD wiring, a real 4-repo build into a temp dir, and an offline guard that a food-delivery surface's
  generated TSX has no over-braced handlers / single-brace styles, exposes `restaurant_id`, and wraps the
  multi-subcollection controls in a fragment.
- `task verify` **2,897 passed** (offline; +9); `task lint`/`security:quick`/`env:check` green; both builder
  demos (152 / 149) unaffected; the R-429 examples still pass `web-typecheck` (no regression). 0 model calls.
