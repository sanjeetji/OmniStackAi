# R-478: Backend — live preview proxy (local-only)

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-19
**Completed:** 2026-09-19

## Objective

Fourth task of the approved 7-task Phase D roadmap (plan record:
`/Users/sanjeet_kumar/.claude/plans/hi-fancy-shannon.md`). Proxy the agent-engine's existing
trusted-local preview control surface — correctly **four** routes, not three, per Finding 3 from
the original planning research: the singleton control surface (`GET /api/preview`,
`POST /api/preview/stop`, `POST /api/preview/restart`) plus the build-scoped one
(`POST /api/history/preview`) a chat-per-build UI actually needs to answer "show me *this* build's
preview." Zero agent-engine changes — every route reused exactly as-is.

## Design

- New routes: `GET /jobs/preview` → `GET /api/preview`; `POST /jobs/preview/stop` →
  `POST /api/preview/stop`; `POST /jobs/preview/restart` → `POST /api/preview/restart`;
  `POST /jobs/build/{id}/preview` → `POST /api/history/preview` with a **server-constructed**
  `{"id": id}` body — the build id comes from the URL path only, the caller's own body is never
  trusted for this one, matching every other build-scoped route in this package. All four
  auth-required, **no credit debit** (viewing/controlling a local preview is not a billable model
  call).
- Generalized `proxyGet` into `proxyUpstream(w, r, deps, method, targetURL, body io.Reader)`
  covering GET and POST alike; `proxyGet` becomes a one-line wrapper (`proxyUpstream(..., nil)`),
  every existing GET route unchanged in behavior.
- **"Not enabled" (build-only mode) passes through for free** — verified by reading
  `live_serve.py`'s `main()`: `status_fn`/`stop_fn`/`restart_fn`/`preview_build_fn` are only wired
  when `OMNISTACKAI_STUDIO_LIVE_PREVIEW` is set; unset, the agent-engine itself returns
  `404 {"error":"preview controls are not enabled"}` for all four routes uniformly. The Go proxy is
  a dumb pipe, so this needs zero new logic — same honest-passthrough property
  `handleBuildFiles`/`handleBuildFile` already have.
- **New `defaultPreviewTimeout` constant** (60s, verified against the real 45s internal wait from
  Finding 4) applied via the same `SetWriteDeadline` pattern `handleBuild` uses, on
  `handleBuildPreview` specifically (it can trigger a real cold start via
  `StudioPreviewManager.replace()`, confirmed by reading `_preview_recorded_build`). The
  fast/synchronous status and stop/restart routes use the ordinary server default.
- **Verified live-preview error shape, not assumed**: an unknown/evicted build's
  `POST /api/history/preview` returns a plain **200** `{"status": "error", "message": "..."}` — no
  exception path in `_preview_recorded_build`, just an error dict returned normally and
  `_send_json(200, res)`'d. A dedicated test asserts this exact 200-with-error-status shape survives
  the proxy unchanged (not silently "fixed" into a 404, which would misrepresent what the
  agent-engine actually returns).

## Acceptance Criteria

- [x] All four routes require authentication (401 with no session) and otherwise proxy the
      agent-engine's response verbatim, including status codes.
- [x] `POST /jobs/build/{id}/preview` always sends `{"id": "<path id>"}` upstream, ignoring any body
      the caller sent.
- [x] The build-scoped route's real 200-with-`{"status":"error"}` shape for an unknown build is
      proxied unchanged, proven by a dedicated test.
- [x] `handleBuildPreview` extends the write deadline via `defaultPreviewTimeout` (60s); the other
      three routes use the server default (`handlePreviewRestart` also extends it, added during
      implementation since restart can trigger the same real cold start as build-preview - see
      Design).
- [x] No credit debit occurs on any of the four routes.
- [x] `go build`/`vet`/`test` and repo `task verify`/`lint`/`security:quick`/`env:check` all pass.

**Design note added during implementation, not in the original plan sketch:** `handlePreviewRestart`
also extends the write deadline via `defaultPreviewTimeout`, not just `handleBuildPreview` - because
`StudioPreviewManager.restart()` can itself trigger a real cold start (confirmed live in step 8
above), the same real risk `handleBuildPreview` has. The plan's own R-479 section already anticipated
this possibility ("cold starts can take up to ~45s") but the original R-478 design sketch only named
`handleBuildPreview`/`handlePreviewRestart` together in one sentence - implemented as written, both
extended.
