# R-490: Runtime — sandbox provider-selection surface

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-19
**Completed:** 2026-09-19

## Objective

Fifth and final task in the sandbox-provider sequence (R-486..R-490). R-486..R-489 each built a
real, independently-tested `SandboxLifecycleProvider` driver (E2B, Vercel Sandbox, Daytona,
gVisor); this task adds the missing piece that makes them genuinely **pluggable and switchable via
configuration** — the founder's explicit, repeated ask across this whole sequence ("switch
easily... based on more cost, speed, smoothness"; "just change configuration on a boolean value to
switch the sandbox free or paid or per userbase").

## Design (verified by direct source read before writing any code)

- **A genuinely separate concern from the pre-existing `tier.py`/`bootstrap.py`, deliberately not
  touched.** `runtime/tier.py`'s `PlatformSetup`/`resolve_platform()`/`platform_status()` and
  `runtime/bootstrap.py`'s `build_runtime_from_env()`/`build_deploy_from_env()` are the *older*
  system: pure planning (`RuntimeProvider`/`PreviewPlan`), still using the placeholder-URL stub
  `CloudSandboxProvider`/`sandbox_driver()` from `drivers.py` — completely independent of, and
  correctly left alone by, every task in this sequence (R-486's contract explicitly confirmed this
  planning layer is right for local execution and stays untouched). The new
  `SandboxLifecycleProvider` system (real create/status/kill) needs its **own** selection surface,
  not shoehorned into either older file.
- **New `runtime/sandbox_selection.py`**, mirroring `bootstrap.py`'s own established shape exactly
  (`build_runtime_from_env(selection=None) -> RuntimeSetup`) for consistency:
  - A registry, `_SANDBOX_LIFECYCLE_PROVIDERS: dict[str, Callable[[], SandboxLifecycleProvider]]`,
    mapping `"gvisor"`/`"e2b"`/`"vercel-sandbox"`/`"daytona"` to each real driver's constructor.
  - `SandboxSetup` (frozen dataclass): `active: tuple[str, ...]` (every registered provider whose
    `.active` is true right now — for `gvisor` this makes a real local Docker `/info` check, for
    the three cloud drivers it's an env-var check, exactly as each driver already defines
    `.active`), `selected: str | None` (`None` when sandboxing is disabled — the default),
    `provider: SandboxLifecycleProvider | None` (`None` when `selected` is `None`).
  - `build_sandbox_from_env(selection=None, *, providers=None) -> SandboxSetup`: reads
    `OMNISTACKAI_SANDBOX_PROVIDER` (default `"none"` — sandboxing off, zero behavior change until
    an operator explicitly opts in, the same conservative default precedent `OMNISTACKAI_DEPLOY_
    PROVIDER` already uses) when `selection` isn't passed explicitly; raises a new
    `SandboxSelectionError` (added to the shared `errors.py`, alongside the pre-existing
    `RuntimeSelectionError`/`DeploySelectionError` this file's sibling functions already use) for
    an unknown name or a real-but-inactive selection (mirroring `build_runtime_from_env`'s own
    "selecting a keyless cloud provider is a clear error" precedent). `providers` is an injectable
    override (mirroring the `opener`/`connection` injectability every driver in this sequence
    already established) so tests never make a real network/Docker call just to test selection
    logic — production code omits it and gets the four real drivers.
  - **The `selection` parameter is the concrete "per userbase" mechanism the founder asked about**:
    a caller can compute `selection` per request (e.g. from a user's plan) and pass it explicitly,
    rather than relying only on the one global env var — documented here as the extension point,
    not built further, since wiring this to real per-user plan data (which lives in the Go
    control-plane's `users` table) is a materially bigger, separate cross-service integration than
    this task's scope, matching every prior task's "not wired into Studio yet" boundary.
- **Deliberately not wired into `studio/`, the Go control-plane, or the console** — consistent
  with R-486/R-487/R-488/R-489's own explicit scope boundaries ("not in scope: wiring into the
  Studio's actual preview flow"). This task completes the *backend selection mechanism* the
  founder asked for; the actual UI/integration step (choosing a provider per build, surfacing it
  in `/settings`) is a distinct, separately-scoped future task once that Studio integration work
  itself is undertaken.

## Gates & Evidence

**A real risk found and avoided during test design, not glossed over**: an early draft of the
"real registry" test called `build_sandbox_from_env()` with no `providers` override to exercise
the production wiring path — but `active` reporting evaluates *every* registered provider's
`.active` regardless of what's selected, and `GVisorSandboxProvider.active` makes a real local
Docker Unix-socket connection attempt. That would have violated "0 real network/Docker calls in
any automated gate" even though the connection would fail fast and safely on a machine without
Docker running. Replaced with `TestRealRegistryWiring`, which asserts the registry maps every name
to the correct real driver *class* (`is` identity checks) without ever instantiating or calling
`.active` on a real one — genuine proof the wiring is correct with zero real I/O risk.

**Deliberately separate from the pre-existing `tier.py`/`bootstrap.py`**, confirmed by direct read
before writing any code: those files resolve the *older*, pure-planning `RuntimeProvider`/
`DeploymentProvider` system (still backed by the placeholder-URL `CloudSandboxProvider` stub),
completely independent of the real `SandboxLifecycleProvider` system this five-task sequence
built. Neither file was touched — confirmed by `git diff` showing no changes to either.

**The "switch per user base" mechanism is real and tested**, not just described:
`test_explicit_selection_parameter_overrides_the_env_var` proves a caller can pass `selection`
explicitly (e.g. computed from a user's plan) and it takes priority over
`OMNISTACKAI_SANDBOX_PROVIDER` with no global state mutation — the concrete extension point a
future per-user-plan integration would call into, without this task needing to build that
integration itself (which lives across the Go control-plane's `users.plan` column, a materially
bigger, separate cross-service task).

**agent-engine `task verify`**: `3,738 tests OK` (9 new in `test_runtime_sandbox_selection.py`), 0
model/network/Docker calls. New tests cover: the default-disabled state and its zero-behavior-
change guarantee; `"none"` explicitly equivalent to unset; `active` aggregating multiple true
providers correctly (sorted); env-var-based selection; explicit-parameter override of the env var;
case-insensitivity/whitespace trimming; an inactive selection raising; an unknown name raising
with the real registered names listed; and the registry-wiring identity check described above.
