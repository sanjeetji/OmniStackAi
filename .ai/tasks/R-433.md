# R-433: Surface-specific ecosystem data and capability scoping

## Status

DONE (2026-09-13). Fourth brick of the differentiating spine.

## Objective

Make each ecosystem surface a genuinely bounded product rather than cloning the same complete domain model
and all platform actors into every generated app. The deterministic planner must select relevant entities for
the surface, retain required relation targets as read dependencies, distinguish readable from writable
capabilities, declare only the surface actor role, and role-gate authenticated mutations. This must
work for curated R-430/R-431 proposals and validated R-432 refinements without another model call.

## Requirements

- Add an explicit, reviewable read/write entity policy for the ten curated domains, keyed by surface kind.
  Admin/operator/customer scope must follow the existing surface descriptions; the compact domain model may
  remain complete when every entity is legitimately needed.
- For custom/refined domains, match entity names deterministically against the surface's name, kind,
  description, and actor. If no match is defensible, retain the full validated model rather than fabricate a
  choice.
- Compute recursive relation closure. A relation target kept only to satisfy integrity is a read dependency:
  it gets list/get endpoints needed by generated selectors, but no screen or write endpoint. A selected
  read-only entity gets a list screen; only a writable entity gets an editor and mutation endpoints.
- Each surface IR declares exactly one normalized actor role. Permissions are entity-qualified `read`/`write`
  strings based on its actual primary/dependency access. Every POST/PUT/DELETE endpoint requires that role;
  preserve existing unauthenticated GET behavior so generated preview/list flows do not regress before the
  authentication UX brick.
- Keep CRUD and parent-scoped LIST_BY endpoints repository-wired and every resulting IR semantically valid.
  Preserve input entity records exactly; do not mutate or invent fields/relations.
- Python 3.13 standard library only; deterministic and offline.

## Acceptance Criteria

- Food delivery's customer app reads Restaurant/MenuItem but writes only Order. The Courier Dispatch App
  contains Order plus its Restaurant dependency, excludes MenuItem,
  renders Order screens only, and cannot mutate Restaurant. Its sole role is `driver`; all Order mutations
  require `driver`.
- The food-delivery admin surface excludes MenuItem; customer and merchant surfaces retain the entities their
  workflows need. All ten curated-domain complete plans validate without errors.
- A tailored unknown-domain proposal selects name-matched primary entities per surface; ambiguous surfaces
  safely keep the complete model. Repeated planning is byte-stable and makes zero model calls.
- Existing ecosystem CRUD wiring, build behavior, R-432 parsing/provider behavior, and both builder examples
  remain green.
