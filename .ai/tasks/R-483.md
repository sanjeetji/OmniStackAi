# R-483: Fix — dynamic-route slug collision & duplicate FK identifier in the edit-delta path

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-19
**Completed:** 2026-09-19

## Objective

A real, reproducible bug found live during R-481's own manual smoke test (documented in
`.ai/tasks/R-481.md`'s Gates & Evidence), scoped and fixed as its own Tracker ID per the founder's
"complete one by one all" direction. Two independent, compounding defects in the edit-delta codegen
path, both confirmed by direct source investigation before writing any fix:

1. **Dynamic-route slug collision.** A follow-up edit produced a new endpoint whose `{param}` path
   segment was spelled differently (`{counter_id}`) than an existing endpoint's own `{param}` for
   the same resource (`{counterId}`) — a real Next.js dev-server crash:
   `Error: You cannot use different slug names for the same dynamic path
   ('counterId' !== 'counter_id')`.
2. **Duplicate `lib/types.ts` identifier.** An edit's proposed entity declared both an explicit
   field (`counter_id`) and a same-named to-one relation (`counter`) for the same conceptual
   foreign key — the generator emitted the FK column twice, a real `tsc` failure (`TS2300`
   "Duplicate identifier", `TS2687`, `TS2717`).

## Root cause (verified by direct source read, not assumed)

1. **Casing inconsistency between two IR sources, never reconciled.** The full-build prompt
   (`intake/nl_to_ir.py`) has no explicit casing rule for API path `{param}`s — its own worked
   example (`application_ir/examples.py`) uses camelCase (`{postId}`, `{driverId}`). The edit-delta
   prompt (`intake/app_delta.py`) explicitly told the model to use `lower_snake_case` for the
   *entire* path, including `{param}` placeholders. Nothing in `parse_app_delta_proposal` or
   `apply_app_delta` reconciled a new endpoint's param spelling against an existing endpoint's own
   param for the same resource — `apply_app_delta` never even calls `normalize_ir()` (confirmed:
   only `intake/nl_to_ir.py`'s full-build path does).
2. **`_entity_interface()` never checks for an existing field before synthesizing a relation's FK
   column.** `codegen/nextjs.py`'s `_entity_interface` (the `lib/types.ts` generator) computes
   `declared = {field.name for field in entity.fields}` but only consults it for
   `created_at`/`updated_at`/`created_by` — for every to-one relation it unconditionally appends
   `f"{relation.name}_id"` with no check against `declared`. `Entity.__post_init__` validates
   field-name uniqueness and relation-name uniqueness as two *separate* sets, never cross-checking
   that a relation's implied FK column doesn't collide with an already-declared field. Confirmed
   this exact shape (an entity with both a `post_id` field and a `post` relation) already sat,
   unexercised for this, in `tests/test_app_delta.py`'s own `_VALID_DELTA` fixture.

Both defects are deterministic, systemic code/prompt facts — not one-off model randomness — and
reproduce reliably for any entity/resource name, not just "Counter".

## Design

1. **`ApiEndpoint.__post_init__` (`application_ir/ir.py`) now canonicalizes every `{param}` to
   camelCase unconditionally**, via a new pure `_canonicalize_path_params()` helper (idempotent —
   an already-camelCase or single-word param like `{id}` passes through unchanged). Applied at the
   one place every `ApiEndpoint` is ever constructed — fresh build, edit delta, solution packs,
   ecosystem packs, and any future caller — closing the bug class structurally, not just at the two
   call sites currently known to be affected. Both prompts (`nl_to_ir.py`, `app_delta.py`) also had
   their instructions corrected to ask for camelCase `{param}`s and explicit reuse of an existing
   resource's param name, as a first line of defense (the code-level fix is the real guarantee).
2. **`_entity_interface()` (`codegen/nextjs.py`) now skips the synthesized `<relation>_id` field
   when a same-named field is already explicitly declared** — the explicit field's own declaration
   always wins; the synthesized one is only ever a convenience for entities that don't declare it
   themselves.

## Scope boundary

- Fixes the two specific defects found live; does not add new cross-collision detection between
  entity fields and relations beyond the one exact shape observed (same-name FK).
- Does not change `_route_dir()` or any other `codegen/nextjs.py` route-generation code — confirmed
  it already correctly mirrors whatever param name the IR gives it; the bug was upstream, in the IR
  itself, not in how the generator renders a folder name from it.
- No changes to `apps/console-web` or `services/control-plane` — this is purely an agent-engine
  codegen/IR correctness fix.
