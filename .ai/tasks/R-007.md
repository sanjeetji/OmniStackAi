# R-007 — Balanced Model Gateway router

## Requirement

Add the platform-owned Model Gateway router that decides which registered `ModelProvider` handles a
request, so product/domain code never selects a provider (Brief §18, §18.3, §84; non-negotiable
§92.4). This is the third foundational model-boundary piece after R-005 (contract + registry) and
R-006 (Ollama adapter), and the smallest next Stage 0/MVP dependency.

The supplied tracker omits R-007 through R-009. This task is reconstructed from Brief Sections 18,
18.1, 18.2, 18.3, 25, 26, 27, 74, 75, 77, 83, 84, 85, 91, and 92 with the founder's standing
instruction to continue one Tracker ID at a time.

Founder intent (2026-09-06): support both API-key cloud LLM providers and local Ollama, added one
Tracker ID at a time. R-007 delivers the routing seam; the first cloud API-key adapter is deferred to
R-008 and requires an explicit founder decision on the specific paid provider before implementation.

## Acceptance criteria

- The router resolves a provider purely from deterministic inputs — task complexity, routing mode,
  registry state, and the model descriptor — with no provider-specific knowledge leaking into product
  code.
- L0 (deterministic) work is rejected from model dispatch with a stable typed error; the router never
  issues a model call for work a deterministic tool should perform (§18.1).
- Under Balanced routing, L1 and L2 work resolves to the local Ollama provider when it is registered
  and healthy (§84).
- L3 and L4 work returns a stable escalation-required outcome because no cloud provider is registered;
  high-risk work is never silently downgraded to the local model.
- When the resolved local provider reports `UNAVAILABLE` health, the router returns a stable
  provider-unavailable outcome and never silently escalates to an unregistered/unauthorized cloud
  provider.
- A conservative deterministic budget guard rejects a request whose estimated input exceeds the model
  safe-input budget or whose requested output exceeds the model max-output budget, rather than
  silently truncating (§85, §18.2; non-negotiable §92.6).
- On a routable, in-budget decision the router dispatches to the provider `generate`/`stream` and
  returns the existing vendor-neutral records unchanged.
- Standard-library tests cover L0 rejection, L1/L2 local routing, L3/L4 escalation-required,
  unavailable-provider no-fallback, budget overflow, empty/unknown registry, and a successful dispatch
  through a fake in-memory provider, all without network access.
- No provider SDK/dependency, cloud provider/call, routing to cloud implementation, service process,
  database or Compose change, infrastructure, new top-level folder, or native/device work is added;
  static `task verify` stays network-independent.

## Design notes

- New `gateway.py`: `TaskComplexity` (L0–L4) and `RoutingMode` (Balanced) enums, a validated
  `RoutingTask` record (complexity + routing mode + `GenerateRequest`), a `RoutingDecision`/dispatch
  path, and a conservative token estimator used only for the budget guard.
- New errors in `errors.py` following the existing stable-`code` pattern:
  `DeterministicWorkNotRoutableError`, `NoEligibleProviderError`, `ContextBudgetExceededError`.
- The L3/L4 branch is pre-wired to look up a cloud provider from the registry and returns
  `NoEligibleProviderError` until R-008 registers one — no router change needed when the cloud adapter
  lands.

## Model and cost trace

Routing is deterministic and needs no model call to implement or test. Deterministic brief and
repository evidence define the implementation. No cloud model is chosen or called (cloud_calls = 0).
