# R-466: Compile-Level Repair for LLM-Written UI + Rate-Limit-Aware Pacing in the Model Gateway

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-17
**Completed:** 2026-09-17

## Objective

Second brick of the founder-approved hybrid engine, driven by what the R-465 live run proved:

1. **The model gateway cannot pace itself.** `cloud.py::_post_json_sync` collapses every HTTP failure into a
   body-bearing `ProviderHTTPError` with no status code and no `Retry-After`, so a 429 on a small
   tokens-per-minute tier (Groq free tier: 8,000 TPM) aborts the whole hybrid flow even though the provider
   says exactly how long to wait ("Please try again in 6.495s"). R-466 adds a typed
   `ProviderRateLimitedError` (status code + parsed retry-after), and a **bounded, injectable-sleep wait**
   inside the provider's `generate()` so the multi-call flow completes on small tiers — deterministic,
   secret-free, no network under `task verify`.
2. **The R-465 validator is string-level.** An LLM-written page can pass import/brace/export checks and still
   fail `tsc`. `verify/run_verify` records only exit codes. R-466 adds a **capturing compile executor**
   (`tsc --noEmit --pretty false`, parsed into per-file errors) and a **compile-repair loop** that feeds each
   LLM-written file's compiler errors back through R-465's `_repair_message` channel (bounded rounds), falls
   back to the deterministic template per file, and applies the result with a hand-built `ProjectDiff` +
   `edit/apply_diff` (+ one commit as the customer identity). Deterministic files are never rewritten.

Model and toolchain calls stay **opt-in** (the `task agent-engine:ui:synthesize` CLI); `task verify` uses
in-memory stub providers, fake runners and temp dirs only.

## Acceptance Criteria

- [x] `model_gateway/errors.py`: `ProviderHTTPError(message, *, status_code=None, retry_after_seconds=None)`
      exposes both attributes; new `ProviderRateLimitedError(ProviderHTTPError)` with
      `code = "provider_rate_limited"`. Existing constructions (`ProviderHTTPError("msg")`) keep working.
- [x] `model_gateway/cloud.py`: pure `parse_retry_after(headers, body) -> float | None` — `Retry-After` as
      seconds (int/float) or HTTP-date, else a bounded body pattern (`try again in 6.495s` / `250ms` / `1m`),
      else `None`. One `_http_error(error)` builder used by both the JSON and stream paths attaches the status
      code and raises the typed 429 error; the body stays truncated (≤500 chars) and never includes the key.
- [x] `_HttpCloudProvider(..., rate_limit_retries=2, max_retry_after_seconds=60.0, sleep=None)`:
      `generate()` retries the same request after `await sleep(delay)` on `ProviderRateLimitedError` only
      (never on other errors), `delay = retry_after_seconds` when parsed else exponential backoff
      (2s, 4s), never sleeping longer than `max_retry_after_seconds` (a longer ask re-raises immediately);
      bounded by `rate_limit_retries`; `create_cloud_provider` forwards the three knobs. Gateway
      `_RETRIABLE_ERRORS` covers the subclass automatically. Exported from `model_gateway`.
- [x] `verify/compile.py`: `CompileError(path, line, column, code, message)`, `CompileReport(ok, returncode,
      errors, output_tail)` with `errors_by_file()` / `error_count` / `to_dict()`; pure `parse_tsc_output(text)`
      (the `--pretty false` `path(line,col): error TSxxxx: message` format; de-duplicated; POSIX paths);
      `compile_web_project(web_dir, *, runner=None, timeout_seconds=600)` (requires
      `node_modules/.bin/tsc`, else `VerifyError`; injectable runner; default `subprocess.run` with
      captured output); `ensure_web_dependencies(web_dir, *, node_modules_source=None, runner=None)` →
      `"present" | "linked" | "installed"`. Exported from `verify`. Never called by `task verify`.
- [x] `codegen/hybrid_repair.py` (new): `LlmFileSpec(path, prompt, fallback)`; `llm_file_specs(ir,
      user_prompt, *, synthesize_screens)` reproduces exactly the R-465 prompts and template fallbacks for
      `app/page.tsx` and `app/<screen.id>/page.tsx` (grounding computed once); bounded
      `compile_errors_message(errors)`; `repair_compiled_files(...)` sends `[SYSTEM, USER(original prompt),
      ASSISTANT(current file, capped), USER(_repair_message(path, compile errors))]`, validates with
      `clean_and_validate_jsx`, retries on validator rejection only, marks success
      `… (<model>; compile-repair k/N)`, falls back to the template, records a `UiSynthesisOutcome` per file,
      and **never touches a path that is not an LLM-written file**; `build_repair_diff(changes)` → a
      `ProjectDiff` of `MODIFIED` `apps/web/<path>` changes; `compile_and_repair(...)` /
      `compile_and_repair_sync(...)` run compile → repair → apply → recompile for `max_rounds`, reverting
      still-failing LLM files to their templates on the last round, returning
      `CompileRepairReport(rounds, repaired, reverted, untouched_failures, final_ok)`.
- [x] CLI `intake/ui_synthesize_run.py` gains Step 3/3: `ensure_web_dependencies` (honours
      `OMNISTACKAI_WEB_NODE_MODULES` to symlink an existing install; otherwise `pnpm install --ignore-scripts`;
      prints a clean "typecheck skipped" line when the toolchain is missing), `compile_and_repair_sync`, one
      customer-identity commit of the repair diff, per-round error counts and the final verdict. Unchanged
      when the toolchain is absent (build + outcome table as in R-465).
- [x] **Amendment (from the R-466 live runs — facts, not hypotheses):**
      (a) The first CLI run's five UI calls failed instantly with a non-429 HTTP status that the outcome
      record hid behind a bare type name → `last_reason` now carries the status (`ProviderHTTPError(413)`),
      never the body.
      (b) A reproduction showed the 429 path working exactly as built (typed `ProviderRateLimitedError(429)`,
      `Retry-After: 112` honoured) but giving up because 112 s exceeds the 60 s cap → the cap and retry budget
      are env-tunable (`OMNISTACKAI_MAX_RETRY_AFTER_SECONDS`, `OMNISTACKAI_RATE_LIMIT_RETRIES`, read by the
      bootstrap, documented in `.env.example`) and every wait / give-up is logged with the numbers.
      (c) That 429 was the **tokens-per-day** limiter (`Limit 200000, Used 191262`): today's live proofs spent
      the founder's daily Groq budget, so a further full live proof waits for the daily reset or a Gemini key.
      (d) A full grounded UI request is ~9k tokens (5,024 in + 4,096 out; the direct probe succeeded on an
      empty window), and Groq answers 413 when one request alone exceeds the 8k TPM limit → the engine now
      shrinks on a "request too large" rejection (413, or a 400 that says so) and retries: first it drops the
      echoed prior output (merging the corrective text into the prompt turn), then it switches to a
      **compact grounding** (`summarize_data_layer(max_chars=5_000)`, `summarize_components(max_chars=4_000,
      max_names_per_file=1)`, `summarize_design_tokens(max_chars=1_000)`) that keeps every hook signature and
      each component's primary export — bounded by the attempt budget; no other exception is retried.
      `NextjsWebAdapter.generate` computes the compact blocks only when a provider is present (the
      deterministic default is untouched); `llm_file_specs` carries a `compact_prompt`; `_repair_one` shrinks
      the same way. A budget test keeps the compact overview/screen prompts ≤ 14,000 chars for both examples.

- No model, network, Docker, or toolchain calls under `task verify` (fake runners / stub providers only).
- No new dependencies (Python 3.13 stdlib only); no vendor SDKs; no secrets in source/logs/state/tests/commits;

- Do not change the bytes of the deterministic default output; do not rewrite non-LLM files during repair.
- Do not change the Application IR, DB engine (PostgreSQL stays), generated-project contracts, or the
  gateway routing semantics (pacing lives inside the provider adapter; the breaker is unchanged).
- Do not modify or commit the untracked `.claude/` directory.
