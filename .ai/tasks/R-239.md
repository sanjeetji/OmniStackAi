# R-239 — Data-access/repository layer for the generated backends

## Requirement

Turn the R-238 schema into a usable persistence layer (Brief §9/§34/§42): generate a per-entity
data-access layer for both backends so the generated code can read and write the tables. Emitted only
when the IR has entities and `database_strategy=postgres`, alongside the migration. Values are always
parameterized (never string-interpolated); identifiers come from the IR. Pure, deterministic, offline —
no DB connection, no query executed. The R-237 edit loop diffs the repositories on IR change. Committed
directly to `main`. New IDs continue after the backlog's R-010..R-219 (this is R-239).

## Acceptance criteria

- Python backend (entities + postgres) emits `app/db.py` (async psycopg connection helper reading
  `DATABASE_URL`) and `app/repositories/<entity>.py` per entity (`list/get/create/delete`);
  `requirements.txt` gains `psycopg`.
- Go backend emits `internal/store/store.go` (a `database/sql` opener) and `internal/store/<entity>.go`
  per entity (`List/Get/Create/Delete`) scanning into the generated model structs; `go.mod` gains the
  `pgx` require; the model import path matches `go.mod`.
- All query values are parameterized (`%s` / `$N`); table/column identifiers are fixed IR-derived
  strings; an id-only entity still creates via `DEFAULT VALUES`.
- Nothing emitted without entities or without postgres; no previously emitted file (other than
  `requirements.txt` / `go.mod`) changes; output is byte-stable.
- Offline tests cover emission + gating, parameterization (no value interpolation), per-entity files,
  the id-only case, and the dependency additions.

## Design notes

- New `codegen/data_access.py`: `python_data_access_files(ir, slug)` and `go_data_access_files(ir, slug)`
  returning `(path, content)` lists; reuse `schema_sql.table_name`. `schema_sql` gains a public
  `table_name`.
- `backend_python.py` / `backend_go.py`: append the data-access files and add the DB dependency when
  `ir.entities and database_strategy is POSTGRES`.
- No DB connection, no query execution, no network. Standard-library only on the platform side.

## Model and cost trace

Deterministic; no model call, no network, no DB connection. cloud_calls zero.
