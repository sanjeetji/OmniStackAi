## Objective

Named, independent follow-up from the Phase D roadmap (`R_&_D/OmniStackAI_Commercial_Platform_Kickoff_v1.md`'s
"Named, deliberately not in the seven above" list; plan record:
`/Users/sanjeet_kumar/.claude/plans/hi-fancy-shannon.md`). A real, **live** Model Provider settings
page — a Dyad-style "Ready"/"Needs key" status view of the model fabric, and (new, not previously
surfaced anywhere) which provider would actually be used for the *next* real build/edit right now.

## Design

- **Verified, not assumed, before writing any code**: `model_gateway/overview.py`'s
  `platform_overview()` already exists, is real, tested, and metadata-only (never includes a key
  value, only a boolean derived from key-env presence) — but it is only ever used to generate a
  **static, build-time** JSON snapshot (`task console:snapshot` → `apps/console-web/data/
  overview.json`), consumed by the existing **public, unauthenticated** `/fabric` marketing/
  architecture page. No HTTP endpoint anywhere serves this live. `/fabric` itself is out of scope
  here — it's a different, existing surface (a static showcase page, not a settings page); this
  task adds a new, separate, **authenticated, live-polled** page instead of touching it.
- **New, not previously available anywhere**: which provider would actually be selected for the
  next real call. `intake/provider_resolution.py`'s `resolve_generation_provider_from_env()` always
  succeeds (it falls through to local Ollama at the end, never raises for "nothing configured") and
  returns a real `ModelProvider` whose `.provider_id` property names it exactly — calling it is a
  safe, side-effect-free way (aside from a real but lightweight ≤1.5s Ollama reachability ping) to
  report "here is what would actually run your next build."
- **Agent-engine**: new `_provider_status()` in `studio/live_serve.py` returns
  `platform_overview()`'s dict augmented with `activeNow: {providerId, modelId} | null` and
  `activeNowError: string | null`. New zero-arg `GET /api/providers` route in `studio/server.py`
  (new `ProvidersFn = Callable[[], dict]` type, new `providers_fn` param, mirroring the existing
  zero-arg `/api/preview` route's dispatch shape) — wired into `live_serve.py`'s always-on
  `control_kwargs` (build-only mode included: this needs no toolchain or running preview, only env
  and one optional local ping, the same reasoning already established for `edit_fn`/`turns_fn`/
  `problems_check_fn`).
- **Control-plane**: new route `GET /jobs/providers`, auth-required, **no credit debit** (a status
  read, not a model call), plain `proxyGet` — no new timeout constant needed (this is fast: env
  reads plus one ≤1.5s local ping, well under the 15s server default).
- **Console**: new `lib/control-plane.ts` addition (`ProviderStatus` type, `getProviderStatus()`),
  new proxy route `app/api/providers/route.ts`, new authenticated `app/settings/layout.tsx` +
  `app/settings/page.tsx` (auth gate mirrors `app/studio/layout.tsx`'s exact pattern), a new
  `SettingsIcon` (gear) in `studio-icons.tsx` promoted to a small shared icon location it can also
  reach from `/settings` (kept in `studio-icons.tsx` and imported cross-route — the icon set was
  never meant to be Studio-exclusive). Linked from the Studio topbar (a new icon-button next to
  `LogoutButton`) and from the home page's existing link list (`/studio`, `/fabric`, now `/settings`).
- **Page content**: a live "Active now" callout (provider + model, or the honest
  `activeNowError` message) at the top, then the same Provider table shape `/fabric` already
  established (`badge on/off` for Active/Needs key) — reusing the established visual language, not
  a new custom look — populated from the live endpoint instead of the static snapshot.

**A real bug found and fixed during this task's own live smoke test, not a pre-existing platform
issue — introduced by this task's own first draft of `_provider_status()`:** calling
`platform_overview()` *before* `resolve_generation_provider_from_env()` meant the providers list's
`active` flags were computed from `os.environ` *before* `.env` had ever been lazily loaded into the
process (a side effect of `resolve_generation_provider_from_env()`'s own `load_dotenv=True`
default) — so in a fresh process that had never yet handled a real build, every cloud provider
showed "Needs key" even when a real key was configured, while `activeNow` (computed second, after
the dotenv load already happened) correctly named the real provider. An honest, internally
self-contradictory response, not a crash — caught only because the live smoke test used a freshly
started agent-engine process, exactly the scenario a real first-time user would hit. Fixed by
resolving `activeNow` first, then `platform_overview()` second, so both parts of one response see
the same, fully-loaded environment — verified with `env -i ... python3 -c "..."` (a completely
clean environment, guaranteeing no accidental prior dotenv load) both before (reproducing the bug)
and after (confirming the fix) the change.
