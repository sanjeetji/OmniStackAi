# R-485: Console — streaming build UI

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-19
**Completed:** 2026-09-19

## Objective

Fast-follow to R-484 (backend SSE build streaming), completing the founder's "streaming first"
priority: the console's own `/studio` chat now actually shows real, live incremental progress for
a new build, instead of the existing static "Building…" wait, closing the loop R-484 opened.

## Design (verified by direct source read before writing any code)

- **`studio-chat.tsx`'s create-path is already plain-prompt-only.** `sendBuild()` only ever POSTs
  `{prompt}` — it has no Solution Pack/Ecosystem/`hybrid_ui` UI at all (those live only in the
  separate raw-HTML Studio page built in earlier tasks, not this Next.js console). Every build this
  component can ever trigger is therefore exactly the kind R-484's `POST /api/build/stream`/
  `POST /jobs/build/stream` already support — no build-kind branching is needed here.
- **New server-side client `streamBuildApp()` (`lib/control-plane.ts`)**: unlike every existing
  function in this file (which awaits and returns parsed JSON via `callControlPlane<T>`), this
  returns the raw upstream `Response` unparsed, so the proxy route can pipe its body straight
  through without buffering it — the whole point of streaming.
- **New proxy route `app/api/jobs/build/stream/route.ts`**: auth-gates via `getSessionToken()`
  (same 401-if-missing shape as every other proxy route), validates a non-blank `prompt` (same
  400 shape as `app/api/jobs/build/route.ts`), then returns `new Response(upstream.body, {status,
  headers})` — relaying the upstream response through unchanged. This single pipe-through
  correctly handles both real shapes the control-plane can return: a streamed `text/event-stream`
  success body, and a plain buffered `application/json` pre-stream rejection (Solution Pack/
  Ecosystem/`hybrid_ui`, a normal `400`) — neither this route nor the browser needs to branch on
  which one it got; both round-trip correctly through the same code path.
- **`studio-chat.tsx` gains `sendBuildStream()`**, replacing `sendBuild()` as the create-path
  handler: `fetch()` + manual `response.body.getReader()` framing (not `EventSource`, which cannot
  send a POST body) — buffers bytes, splits on `"\n\n"` event boundaries, and parses each frame's
  `data:` line as JSON. Three real shapes to handle, verified against R-484's actual live output
  (not assumed): a `{"phase": "generating_ir", "delta": "..."}` frame (accumulate a running
  character count only — see below), a `{"phase": "done", ...}` frame (the final build result,
  same shape `sendBuild()` already handled), and a bare `{"credit_balance": ..., "credits_spent":
  ...}` frame with **no** `"phase"` key at all (the Go relay's trailing `event: credits` frame —
  confirmed live during R-484 that credits arrive as a *separate* trailing frame, never merged into
  the streaming path's own `"done"` payload, unlike the non-streaming response's shape). A
  `{"phase": "error", ...}` frame surfaces as a normal chat error message.
- **What's shown while streaming, and why**: not the raw IR JSON text itself — token-by-token JSON
  fragments (`{"na`, `me": "`, ...) would render as visibly broken/meaningless to a non-technical
  user, and a real-time partial-JSON-aware renderer is a materially larger feature out of scope
  here. Instead: a live, honest "Generating your app… (N characters so far)" indicator, its count
  ticking up in real time as deltas arrive — proving genuine live activity (the founder's actual
  ask: an engaged, alive feeling from the first response) without fabricating a fake progress
  percentage or showing broken partial JSON. Replaced by the existing full result-card rendering
  the instant the `"done"` frame arrives, unchanged from `sendBuild()`'s own behavior today.
- **The existing non-streaming path is untouched and still real**: `POST /jobs/build` (control-
  plane), `POST /api/build` (agent-engine), `app/api/jobs/build/route.ts`, and `lib/control-
  plane.ts`'s `buildApp()` all remain exactly as they are — genuinely reachable via direct API use,
  simply no longer called by this one UI component now that its create-path uses streaming.
- **Edit stays non-streaming** — R-484's own scope boundary ("build only, not edit"); `sendEdit()`
  is unchanged.

## Scope boundary

- Only the **create** (first-message) path streams. Follow-up edits keep using the existing
  blocking `POST /api/jobs/build/{id}/edit`.
- No new build-kind UI (Solution Pack/Ecosystem/`hybrid_ui` toggles) — out of scope, matches this
  component's existing plain-prompt-only shape.
- No raw partial-JSON/live-diff rendering of the streaming IR text itself — only an honest
  character-count "generating" indicator, per the Design section above.

## Acceptance Criteria

- [x] Submitting a new prompt in `/studio`'s chat streams real incremental progress from the real
      backend, visible as a live-updating character count, not a static "Building…" label.
- [x] The final result (name, entities, file count, files, workspace/tabs) renders identically to
      today's non-streaming path once the `"done"` frame arrives.
- [x] The trailing `credits` frame updates the visible credit balance.
- [x] A streaming error (`"phase": "error"`) surfaces as a normal chat error message, not a crash.
- [x] Follow-up edits are provably unchanged (still call the existing non-streaming edit route).
- [x] `pnpm run typecheck`/`lint`/`build`, and repo `task verify`/`lint`/`security:quick`/
      `env:check`, all pass.
