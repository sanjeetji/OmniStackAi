## Design (verified against real, current Vercel documentation before writing any code)

- **Full endpoint list confirmed** (fetched `vercel.com/docs/rest-api#sandboxes`, the canonical
  index, not a single page in isolation): sandbox creation is `POST /v2/sandboxes` — there is only
  one creation model ("named sandbox"; every sandbox has a `name`, with `persistent: false`
  selecting the non-snapshotting/ephemeral behavior this task needs, rather than a separate
  "unnamed" endpoint, which does not exist). Status: `GET /v2/sandboxes/{name}`. Termination:
  `DELETE /v2/sandboxes/{name}` (deletes the resource entirely — distinct from `POST
  /v2/sandboxes/sessions/{sessionId}/stop`, which only stops a session and can be resumed; `kill()`
  maps to the `DELETE`, matching E2B's own "kill removes the resource" semantics).
- **Auth**: `Authorization: Bearer <VERCEL_TOKEN>` — reuses the *same* env var
  `DEPLOY_SPECS["vercel"]` already declares for the CLI-based deploy path (same underlying Vercel
  account/token, no duplicate credential needed). New `RUNTIME_SPECS["vercel-sandbox"]` entry.
- **A real, additional required config beyond the token**: Vercel's `POST /v2/sandboxes` requires a
  `projectId` — unlike E2B (template-only) or a bare API key, a sandbox must belong to a Vercel
  project that already exists in the account. New `VERCEL_PROJECT_ID` env var (placeholder, no
  value); `create()` raises a clear, typed error when it is unset, exactly like a missing API key,
  rather than sending a request Vercel would reject.
- **`routes[].url` is used directly, not reconstructed** — a real, meaningful difference from E2B:
  Vercel's create-sandbox response returns an explicit `routes` array, one entry per requested
  port, each already carrying its own public `url`. `create()` requests exactly one port (the
  target's port, resolved the same way R-486's `_port_for_target()` already does) and reads that
  route's `url` verbatim, rather than guessing a URL pattern from a template string.
- **A real, honest product limitation, not glossed over**: Vercel Sandbox's documented `runtime`
  enum is `node22`/`node24`/`node26`/`python3.13` — **no Go**. `backend-go` is explicitly rejected
  with a new, specific `UnsupportedSandboxRuntimeError` (distinct from `UnsupportedRuntimeTargetError`,
  which means "no target definition exists at all" — here the target is real and well-defined, but
  *this specific provider* cannot run it natively; a custom OCI `image` field exists in Vercel's
  schema as a real escape hatch, but building and maintaining a Go-capable custom image is
  materially more work than this task's scope, deferred honestly rather than attempted partially).
- **New `runtime/vercel_sandbox.py`: `VercelSandboxProvider`**, implementing
  `SandboxLifecycleProvider` via `sandbox_http.py` (the same shared, stdlib-only safe HTTP helper
  R-486 introduced — proving it is genuinely reusable across differently-shaped provider APIs, not
  E2B-specific).
- **No real credentials exist in this environment** (`VERCEL_TOKEN`/`VERCEL_PROJECT_ID` both
  unset) — every gate is offline via the same injected-fake-opener pattern R-486 established;
  live-cloud verification is honestly deferred, not faked.

## Gates & Evidence

**Vercel's real REST API was verified directly** (fetched the canonical `vercel.com/docs/rest-api
#sandboxes` endpoint index plus the full `create-a-named-sandbox` schema page, not assumed from
training data): `POST /v2/sandboxes` (only creation model — "named", `persistent: false` selects
ephemeral behavior; there is no separate unnamed-sandbox endpoint), `GET`/`DELETE
/v2/sandboxes/{name}` (both keyed by **name**, not the response's `session.id` — a real distinction
this driver gets right: `create()` stores the generated `name` as `SandboxHandle.sandbox_id`, not
`session.id`, so `status()`/`kill()` send the request Vercel actually expects). `routes[].url` is
read directly from the create response rather than reconstructed from a guessed pattern — a real,
meaningful design difference from E2B, made possible because Vercel's own response already
provides it.

**A real, documented product limitation, not glossed over**: Vercel Sandbox's `runtime` enum is
`node22`/`node24`/`node26`/`python3.13` — no Go. `backend-go` is rejected with a specific
`UnsupportedSandboxRuntimeError`, verified by a dedicated test, distinct from
`UnsupportedRuntimeTargetError` (an entirely unknown target, e.g. `"flutter"`) — a real ordering
bug was caught and fixed here: the first draft checked Vercel-runtime-support *before* validating
the target exists at all, so an unknown target like `"flutter"` incorrectly raised
`UnsupportedSandboxRuntimeError` instead of `UnsupportedRuntimeTargetError`; fixed by validating
the target first (via the shared `_port_for_target()` helper, which raises the correct error for a
genuinely unknown target) before checking this provider's own runtime support.

**A real, necessary correction discovered mid-task**: adding `"vercel-sandbox"` to `RUNTIME_SPECS`
broke a pre-existing test (`test_tier_drivers.py::test_every_provider_has_a_driver` and
`test_no_key_value_appears_in_any_plan`), which enumerates every `RUNTIME_SPECS` entry and expects
a matching `_SANDBOX_URLS` placeholder in the old planning-stub path (`drivers.py`). Fixed with a
single added line (`"vercel-sandbox": "https://<name>.vercel.run"`) — `runtime/drivers.py` added to
`allowed_paths` mid-task once the gap was found, following the same discipline as every prior
mid-task scope correction this session; the `CloudSandboxProvider`/`sandbox_driver()` logic itself
is otherwise completely untouched.
