## Objective

Phase B of `R_&_D/OmniStackAI_Commercial_Platform_Kickoff_v1.md`: replace the static, dependency-free
`apps/console-web` (plain HTML/CSS/JS reading a committed `data/overview.json` snapshot) with a real
Next.js (App Router, TypeScript) app, with working register/login/logout screens wired to R-469's
control-plane (`POST /auth/register`, `/auth/login`, `/auth/logout`, `GET /auth/me`), and the existing
model/cost overview carried forward as one page on the same `data/overview.json` data contract — exactly
as the kickoff doc's own README already promised ("The forward path is a Next.js app... the data
contract and the design carry over unchanged").

**Correction to the kickoff doc's own framing, found while starting this task:** the doc says this phase
is "the point where `task bootstrap`/`task doctor` gain a real Node/npm toolchain requirement." That's
not quite right — `scripts/doctor.sh` already lists `node`/`pnpm` as required commands (added when the
control-plane's monorepo scaffold was bootstrapped, apparently in anticipation of this). What's actually
new here is that `pnpm install` will, for the first time, need to fetch real packages (`next`, `react`,
etc.) rather than resolving an empty workspace — confirmed npm registry is reachable from this machine.

## Architecture decisions

- **Session handling: server-side cookie proxy, not a browser-held bearer token.** The Next.js app never
  hands its raw session token to client-side JavaScript. Route Handlers under `app/api/auth/*` proxy to
  the control-plane server-to-server (no CORS needed — the browser only ever talks to the Next.js origin)
  and set/clear an `httpOnly`, `sameSite=lax` cookie holding the token. This is a deliberate improvement
  over a naive `localStorage` token (which is readable by any injected script) and costs only a few small
  Route Handlers — worth doing correctly now rather than reworking later on a "fully commercial" product.
- **No new UI dependency beyond React/Next.js itself** (no Tailwind, no component library). The existing
  console's own design tokens (CSS custom properties in `styles.css` — indigo accent, light/dark via
  `prefers-color-scheme`, card/badge/table language) carry forward into `app/globals.css`. A real design
  system is Phase D's job, once the actual Studio UX is rebuilt on this foundation — scope discipline, not
  an aesthetic judgment.
- **`OMNISTACKAI_CONTROL_PLANE_URL`** (new env var, default `http://127.0.0.1:8080`) is the URL the
  Next.js server calls the control-plane on — kept distinct from the control-plane's own
  `OMNISTACKAI_CONTROL_PLANE_ADDRESS` (what it binds to) since those could differ once either side is
  actually deployed. Server-side only (no `NEXT_PUBLIC_` prefix — the browser never needs it).
- **`data/overview.json` stays a committed, Python-refreshed snapshot** (`task console:snapshot`,
  unchanged) — the new "Model Fabric" page imports it directly as a build-time JSON module, same data
  contract as before, now rendered by a React Server Component instead of hand-written DOM JS.

## Live discovery (found while implementing, not anticipated in the contract)

- **`pnpm install` timed out downloading `next` and `@next/swc-darwin-arm64` (curl error 23,
  connection aborted) on the first two attempts** — a raw `curl` of the same 41.7 MB `next` tarball
  succeeded but took ~50s on this network, right at the edge of pnpm's default per-attempt fetch
  timeout. Fixed with a new root `.npmrc` (`fetch-timeout=300000`, `fetch-retries=5`, generous
  retry backoff) — a legitimate, minimal robustness fix for a slow-network sandbox, not a scope
  change.
- **`typescript@7.0.2` (the actual current `latest` on the npm registry) is not yet supported by
  `typescript-eslint@8.70.0`** (`eslint-config-next`'s dependency): `eslint` refused to run at all
  ("typescript-eslint does not support TS 7.0"). Confirmed `eslint-config-next@16.3.5`'s own
  `devDependencies` pin `typescript: 6.0.2` — pinned the console to `typescript: 6.0.3` (latest
  6.x) instead. `tsc --noEmit` itself works fine under either version; this is purely an
  ecosystem-tooling lag, not a real TypeScript compatibility problem.
- **`eslint.config.mjs` using the documented `FlatCompat` + `compat.extends("next/core-web-vitals",
  "next/typescript")` pattern crashed** with `TypeError: Converting circular structure to JSON`
  inside `@eslint/eslintrc`'s schema-error formatter (tried on both `eslint@10.10.0` and
  `eslint@9.9.1` — same crash either way, so it was never actually an ESLint-version issue).
  Root cause: `eslint-config-next@16.3.5`'s default export (`dist/index.js`) is already a native
  flat-config array — the legacy `FlatCompat` shim is unnecessary for this version and its
  validator chokes on a circular self-reference inside `eslint-plugin-react`'s own flat config
  export when trying to format an unrelated error. Fixed by importing `eslint-config-next`
  directly (`import nextConfig from "eslint-config-next"; export default [...nextConfig, {...}]`)
  and dropping the `@eslint/eslintrc` dependency entirely — simpler and it actually works. Kept
  `eslint@9.9.1` (matching the package's tested peer range) rather than churning back to 10.x.
- **`pnpm install` refused to run `unrs-resolver`'s (an ESLint transitive dependency) postinstall
  script** (`ERR_PNPM_IGNORED_BUILDS`), which then made `pnpm run <script>` itself fail via an
  internal dependency-freshness re-check. `package.json`'s `pnpm.onlyBuiltDependencies` field
  turned out to be a dead end — pnpm 11.19 silently stopped reading `pnpm.*` keys from
  `package.json` (warned as much) and moved the setting to `pnpm-workspace.yaml`'s `allowBuilds`
  map instead, which is what's actually committed here.
- **The cookie's `Secure` flag was wired from `NODE_ENV === "production"`, which is wrong**: `next
  start` always sets `NODE_ENV=production` regardless of the real protocol, so every cookie this
  app issued locally over plain `http://127.0.0.1` was marked `Secure` — harmless in the curl-based
  first smoke test (curl doesn't enforce the attribute), but a **real browser refuses to send a
  `Secure` cookie back over a non-HTTPS origin**, which would have silently broken login
  persistence for anyone actually using this app locally. Caught by inspecting the first smoke
  test's raw `Set-Cookie` header rather than trusting the 200/204 status codes alone. Fixed with a
  new `isSecureRequest(request)` helper (checks `x-forwarded-proto` then the request's own
  `nextUrl.protocol` per-request, not a static env check) used by all three auth routes; re-ran the
  full smoke test afterward and confirmed the cookie is now issued **without** `Secure` over plain
  HTTP (verified directly in curl's own cookie-jar file, whose 4th field is the secure flag).
