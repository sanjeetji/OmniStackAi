# R-284 — Server-Side Field Filters for FK-Scoped Subcollections

**Status:** done
**Phase:** BASIC/MVP — Founder Stage 0
**Branch:** `main`
**Complexity:** L2 (deterministic code generation; 0 model calls)

## Objective

Extend R-282's allowlisted boolean/enum equality filters from top-level collection routes to
unambiguous FK-scoped `LIST_BY` subcollection routes. Generated FastAPI, Go, and OpenAPI output must
agree on the query contract while relation scoping remains mandatory and every runtime value stays
parameterized.

## Scope and impact

- Change only the existing data-access, FastAPI handler, Go handler, and OpenAPI generators plus
  focused offline tests.
- Reuse `field_validation.filter_fields`; no Application IR or schema-version change.
- Backend/API contract only. Generated Next.js subcollection controls are unchanged.
- No dependency, database connection, external request, model call, infrastructure, or native/mobile
  work.

## Acceptance criteria

1. Python `list_*_by_*` and `count_*_by_*` accept boolean/enum filter kwargs and compose relation scope,
   optional `q`, and equality predicates using `%s` parameters in deterministic order.
2. FastAPI `LIST_BY` routes declare typed optional filter query parameters and pass the same values to
   count and list repository calls.
3. Go `List*By*` and `Count*By*` accept a filters map and share a relation-scoped predicate builder.
   Relation ID is `$1`; search, filters, limit, and offset receive subsequent placeholders.
4. Go handlers call `parseFilters` and forward the map only when the child entity is filterable.
5. OpenAPI `LIST_BY` operations document the same boolean/enum schemas as top-level `LIST`.
6. Non-filterable subcollections retain their existing generated signatures and SQL; description-only
   IR changes remain byte-identical.
7. Full offline verification, lint, security, both builder demos, and generated-artifact inspection pass.
