# R-472: Bridge the control-plane's Job API to the agent-engine — real credit debiting

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-17
**Completed:** 2026-09-18

## Objective

Phase C of `R_&_D/OmniStackAI_Commercial_Platform_Kickoff_v1.md` (renumbered from R-471, which
became a real bug-fix task instead — see `.ai/tasks/R-471.md`): the control-plane's Job API proxies
"build this app" requests to the existing agent-engine, and a real generation call actually debits
the authenticated user's credit balance, with local-Ollama usage staying credit-exempt.

## Correction to the kickoff doc's own framing, found while researching this task

The kickoff doc says this bridges to the "unmodified" agent-engine. That is not quite achievable if
credit debiting is to be based on *real* token/cost data rather than a guess, because:

- `intake/build_app.py::app_build_result_to_dict` does not include any usage/cost data today.
- The Studio's actual generation path (`intake/provider_resolution.py::
  resolve_generation_provider_from_env`) returns a **raw** `ModelProvider` — for the cloud path it
  extracts `boot.registry.get(boot.cloud_tier_provider_id)` out of a `ModelGateway`'s registry and
  returns that raw provider, not the gateway itself. The `ModelGateway`'s own accounting hook
  (`model_gateway/accounting.py::UsageLedger`, `gateway.py`'s `_record`) is real and already
  tested, but it is only ever exercised today by `console_snapshot.py` for the illustrative
  metadata dashboard — **it is not wired into any real Studio build or edit call.** Confirmed by
  grep: no `UsageLedger`/`record_call` reference anywhere in `studio/` or `intake/build_app.py`.

So this task makes a small, additive, non-invasive agent-engine change — a decorator that
implements the exact same `ModelProvider` protocol every existing call site already depends on, so
none of them need to change — rather than leaving agent-engine literally untouched.

## Architecture decisions

- **`RecordingProvider` (new, `model_gateway/recording.py`):** wraps any `ModelProvider`, forwards
  every method call to the inner provider unchanged, and records every `generate()` call (success
  or failure) into an injected `UsageLedger` — the same, already-tested ledger/pricing primitive
  `console_snapshot` uses for its illustrative numbers, now doing real accounting for real calls.
  Every existing call site (`codegen/llm_ui.py`, `intake/nl_to_ir.py`, `intake/app_delta.py`, ...)
  is unaffected — they already just call `.generate()` on whatever provider object they're handed.
- **`resolve_generation_provider_from_env(..., usage_ledger: UsageLedger | None = None)`:** when
  given, wraps whatever provider is resolved (local or cloud) in `RecordingProvider`. Omitted
  (the default) reproduces exactly today's behavior — every existing caller and test is unaffected.
- **A fresh `UsageLedger` per HTTP request, not a shared/global one.** `studio/live_serve.py`'s
  `_build` (and, named as an explicit follow-up, `_edit`) creates one, passes it in, and after the
  build reads `ledger.summary()` for a JSON-safe usage block in the response — additive, mirroring
  exactly how R-467 added `ui_outcomes` (a new optional key, omitted when not applicable, every
  existing response shape byte-for-byte unchanged otherwise).
- **Cost crosses the Go/Python boundary as an integer, not a decimal string.** The agent-engine
  reports `cost_micros_usd` (an `int`, `cost_usd * 1_000_000`, rounded) instead of a `Decimal`
  string — Go has no standard-library arbitrary-precision decimal, and parsing a decimal string
  cross-language is exactly the kind of float/precision risk this project avoids elsewhere. An
  integer micro-dollar amount is exact and trivial to convert to credits with plain `int64` math.
- **Local-Ollama usage is already zero-cost** (`DEFAULT_PRICE_BOOK`'s `("ollama-local", None):
  ModelPrice("0", "0")`, from before this task) — `cost_micros_usd` naturally comes out `0` for a
  local-only build, so it naturally debits `0` credits without any special-casing in the credit
  math. A `local_only: bool` is still reported for an honest ledger reason string
  ("generation:local" vs "generation:cloud") and for future UI use, not because the math needs it.
- **The control-plane's `/jobs/build` is a generic proxy, not app-generation-aware.** It forwards
  whatever JSON body the client sent straight to the agent-engine's `POST /api/build` unchanged,
  parses the response only enough to find a top-level `usage` object if present, and returns the
  agent-engine's own response body augmented with `credits_spent`/`credit_balance` — it does not
  need to understand plain-prompt vs. Solution Pack vs. Ecosystem shapes, matching "control-plane
  proxies... agent-engine reused as-is" for everything except the one new response field.
- **v1 credit policy: never block a build, clamp instead of going negative.** A build attempt
  proceeds regardless of current balance (there is no reliable way to know in advance whether a
  given deployment will route to local or cloud — that is environment-configured, not a per-request
  choice the caller makes). After the real cost is known, the debit is clamped so
  `credit_balance` never goes below zero; the actual amount charged (which may be less than the
  full cost, if the balance ran out mid-build) is what's recorded in the ledger and returned to the
  caller. Hard pre-flight blocking on insufficient balance is a deliberate, named follow-up, not
  silently skipped — it needs a real UX for "you're out of credits" that doesn't exist yet.
- **No console-web changes.** Per the kickoff doc, Phase C is control-plane + agent-engine only;
  the Studio UX itself (a page that actually calls `/jobs/build`) is Phase D, built once this
  backend foundation exists.

## Scope (v1)

**In scope:** `RecordingProvider`; threading a per-request `UsageLedger` through
`resolve_generation_provider_from_env` and the Studio's `_build` flow only (not `_edit` — named
follow-up); `app_build_result_to_dict`'s additive `usage` key; the control-plane's new
`internal/jobs` package (`POST /jobs/build`, authenticated, proxies to the agent-engine, debits
credits); a reusable `auth.RequireUser` helper so `internal/jobs` can authenticate requests without
duplicating `internal/auth`'s bearer-token/session-lookup logic; `users.Store.DebitCredits`
(atomic, row-locked, clamped); two new env vars (`OMNISTACKAI_AGENT_ENGINE_URL`,
`OMNISTACKAI_CREDITS_PER_USD`).

**Out of scope, named for follow-ups:**
- `/jobs/build/{id}/edit` (mirroring `/jobs/build` for R-468's edit flow) — same shape, deferred to
  keep this task to one generation path first.
- Hard pre-flight blocking when a user has zero credits — needs its own UX design, not a silent
  default.
- Any console-web UI that actually calls `/jobs/build` — Phase D.
- Running the agent-engine's Studio server via Docker Compose — `scripts/test.sh` already
  hard-blocks adding it as a Compose service at this stage (`R-004`'s "exactly postgres +
  control-plane" contract); the control-plane reaches it via a configurable URL instead, and a
  developer starts it the same way `COMMANDS.md` already documents
  (`task agent-engine:studio:serve`/`:preview`).
- Solution Pack / Ecosystem build cost accounting specifics — the generic proxy handles whatever
  the agent-engine returns; no special-casing needed or added.

## Live discovery (found while implementing, not anticipated in the contract above)

- **Real bug caught by the new tests themselves, fixed before any commit:** the first
  `RecordingProvider.generate()` draft recorded `provider_id`/`model_id` from the *response's own*
  `response.model` field. `ModelGateway._record` (the pattern this decorator is supposed to mirror)
  instead uses `decision.provider_id`/`decision.model.model_id` — the actually-dispatched
  provider/model, not whatever the response happens to echo back. `test_recording_provider.py`'s
  local-Ollama test caught the mismatch immediately (`cost_usd` came back `None`/wrong tier because
  the recorded identity didn't match the provider that was actually called). Fixed to source both
  fields from `self._inner.provider_id`/`request.model.model_id`, matching the gateway exactly.
- **Scope trim: `usage` threading is plain-prompt-only, not "any provider was actually used."**
  `_build`'s Solution Pack and Ecosystem branches also call `resolve_generation_provider_from_env`,
  but `CURRENT_TASK.yaml`'s own allowed-paths list never included `solution_packs/*` or the
  ecosystem code paths — only the plain-prompt branch (the one this task's own "Correction to the
  kickoff doc's framing" section is about) was in scope. `internal/jobs`'s proxy already handles a
  missing `usage` key honestly (0 credits charged, not an error), so Solution Pack/Ecosystem builds
  stay free until a follow-up threads a ledger through them too.
- **Dropped the planned `local_only` field from the usage summary.** The per-request `UsageLedger`
  can (in principle) span more than one call across more than one tier reason within a single
  build (e.g. `generate_ir` + overview-page synthesis, which can differ if one path falls back);
  a single top-level boolean would be a lossy simplification nothing downstream actually needs —
  `internal/jobs` only ever reads `cost_micros_usd`, and local usage already reports `0` there
  without any special-casing.
- **Credits rounding changed from ceiling to nearest, contradicting this file's original plan.**
  The plan above originally said "ceiling-rounded so the platform never under-charges." On
  reflection, ceiling rounding systematically *overcharges* every single build by up to just under
  one credit, which compounds over volume; round-to-nearest (`math.Round`) is the more honest
  figure at this granularity (`OMNISTACKAI_CREDITS_PER_USD=1000` means 1 credit = $0.001), and the
  exact real cost stays fully visible in the response's `cost_micros_usd` for any future audit or
  reconciliation need. Implemented as round-to-nearest in `jobs.creditsForUsage`, table-tested.
- **Real infrastructure bug found only by the live smoke test, not by any unit test:** the
  control-plane's `http.Server` has a global `WriteTimeout` (default 15s, tuned for fast routes
  like `/auth/*`). `/jobs/build` proxies a slow, multi-model-call upstream operation that routinely
  takes 1-3+ minutes for a real build; the server was silently killing the connection mid-build,
  so the client saw a connection reset (`curl` reported `http_status=000`) even though the build
  completed successfully server-side moments later. Fixed with
  `http.NewResponseController(w).SetWriteDeadline(time.Now().Add(defaultBuildTimeout))` scoped to
  just this one handler, leaving the server-wide timeout (real slow-loris protection for every
  other route) untouched.
- **Compose networking gap:** the agent-engine's Studio server runs on the host (Compose is
  hard-blocked from adding it as a service), so the containerized control-plane cannot reach it via
  `127.0.0.1` (that resolves to the container itself). Fixed by defaulting
  `OMNISTACKAI_AGENT_ENGINE_URL` to `http://host.docker.internal:4173` and adding
  `extra_hosts: ["host.docker.internal:host-gateway"]` to the `control-plane` service (portable to
  Linux Docker Engine, not just Docker Desktop/Colima where the alias already exists). Verified
  reachable from inside the running container under Colima before attempting the real smoke test.
- **Live-proof design choice: local Ollama, not the environment's real configured cloud provider.**
  This machine's `.env` sets a real `OMNISTACKAI_CLOUD_PROVIDER=groq` with a live `GROQ_API_KEY` (the
  platform's actual intended default, not a test fixture). The *first* smoke attempt used that
  default unmodified and incurred one small, real Groq API call before failing at IR-parsing (the
  model's output didn't structurally validate) — an honest, incidental real cost, though not one
  this task's changes could have prevented or priced (the build failed before any usage summary was
  ever computed, so nothing was charged for it either). All subsequent attempts forced
  `OMNISTACKAI_PREFER_LOCAL=1` so the rest of this task's live verification is reproducible and
  free. Because a genuinely free local build has nothing to debit, the row-locked `DebitCredits` SQL
  path itself was proven separately, directly against the same live Postgres, via a small throwaway
  Go program (imported `internal/users`, never committed, deleted immediately after) — see below.
