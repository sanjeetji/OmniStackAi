# R-231 — Application IR validator/normalizer + example fixtures

## Requirement

Harden the Application IR (Brief §9/§12/§66) with: a **semantic validator** (checks beyond per-record
construction), a deterministic **normalizer** (canonical sorted IR for stable diffs), and realistic
**example IR fixtures** that drive the adapters. Standard-library only, deterministic, offline. Work
committed directly to `main`. New IDs continue after the workbook backlog's R-010..R-219 (this is
R-231).

## Acceptance criteria

- `validate_ir(ir)` → deterministic, ordered tuple of typed `Issue`s (severity error|warning, stable
  code, message, location): an API `request/response/error_schema` referencing an undeclared entity is
  an **error**; a web/admin/mobile strategy set without the matching platform (or the reverse) is a
  **warning**. A clean IR yields no errors.
- `normalize_ir(ir)` → a new `ApplicationIR` with platforms in enum order and
  roles/entities/apis/screens/acceptance sorted canonically (entity field order preserved); idempotent
  and lossless through `to_dict`.
- `example_ir(name)` → ≥2 realistic, construction-valid IRs that pass `validate_ir` with no errors and
  generate via the web/Python/Go adapters.
- Standard-library only; deterministic; no network/model call; `task verify` stays green.
- Offline tests cover each rule (error + warning), a clean IR, normalize sorting/idempotency/round-trip,
  and example validity.

## Design notes

- `application_ir/validate.py`: `Severity`, `Issue`, `validate_ir`, `normalize_ir`. The validator is
  additive — it never weakens the hard construction checks in `ir.py`.
- `application_ir/examples.py`: builder functions returning `ApplicationIR` (e.g. rideshare-favourites,
  minimal-blog) + `example_ir(name)` / `EXAMPLES`.

## Model and cost trace

Deterministic; no model call. No cloud key set; cloud_calls zero.
