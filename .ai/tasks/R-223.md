# R-223 — Env-driven fallback chain and circuit breaker wiring

## Requirement

Make R-221's cross-provider fallback and circuit breaker configurable from the environment via
`build_gateway_from_env`, so operators enable resilience without code (Brief 18.3, 89). New IDs
continue after the workbook backlog's R-010..R-219 (this is R-223).

## Acceptance criteria

- `OMNISTACKAI_FALLBACK_PROVIDERS` (comma-separated, ordered) builds a fallback chain from already
  registered providers — `ollama` for local, or a cloud provider name. An unknown name, or a named
  provider whose key is not set, raises a clear `CloudProviderSelectionError`.
- A `CircuitBreaker` is attached to the gateway **only when a chain is configured**, using
  `OMNISTACKAI_CIRCUIT_FAILURE_THRESHOLD` (default 3) and `OMNISTACKAI_CIRCUIT_COOLDOWN_SECONDS`
  (default 30).
- With no chain configured, `build_gateway_from_env` is behaviorally identical to before.
- `GatewayBootstrap` exposes the chain provider ids + breaker settings; the overview snapshot and
  console render a resilience panel; no key/secret appears anywhere.
- Offline tests cover chain building, unknown/no-key errors, breaker attachment, the unchanged
  default, and the snapshot fields; `task verify` stays green.

## Design notes

- `build_gateway_from_env`: after registering providers and selecting the cloud tier, parse
  `OMNISTACKAI_FALLBACK_PROVIDERS`, resolve each name to its registered descriptor (`ollama` →
  ollama descriptor; cloud name → its cloud descriptor, else error), pass as `RoutingPolicy.fallback`,
  and attach a `CircuitBreaker` when the chain is non-empty.
- `overview.py`: add a `resilience` block (fallback provider ids, breaker enabled/threshold/cooldown)
  read from env; `app.js` renders a "Resilience" panel.

## Model and cost trace

Deterministic; no model call. No cloud key set; cloud_calls zero.
