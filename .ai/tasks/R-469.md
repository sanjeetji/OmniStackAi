# R-469: Control-plane foundation — users, auth, plans, credits

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-17
**Completed:** 2026-09-17

## Objective

Phase A of `R_&_D/OmniStackAI_Commercial_Platform_Kickoff_v1.md` (the founder-approved commercial
platform kickoff, 2026-09-17): give the existing `services/control-plane` Go skeleton (currently
health-check-only, one migration that only creates `schema_migrations` + enables `pgvector`) real
users, authentication, and a plan/credit model, so a real signed-up user can exist before any
frontend or agent-engine bridge is built (those are Phases B/C, separate Tracker IDs).

Two roles only (`super_admin`, `user`); access for `user` is gated entirely by `plan`, not a
second role tier. Plans reuse the tier names already named in
`R_&_D/OmniStackAI_Implementation_Brief_v6.md` Section 22 (`free`/`developer`/`pro`/`agency`/
`enterprise`, `byok` as an add-on flag). Every signup gets the `free` plan and a starting credit
grant; the credit ledger and gating logic for actually *spending* credits on generation calls is
Phase C's job (needs the agent-engine bridge, which doesn't exist yet) — this task only needs the
ledger to correctly record the signup grant.

## Scope (v1)

**In scope:**
- Migration `000002_users_auth_billing`: `users` (id, email, password_hash, role, plan,
  byok_enabled, credit_balance, created_at, updated_at), `credit_ledger` (append-only, records
  every balance change with a reason), `sessions` (opaque bearer tokens, stored only as a SHA-256
  hash, never the raw token).
- A small embedded migration runner (`migrations` package, `//go:embed *.up.sql`) so the
  control-plane self-heals its schema on every boot regardless of whether the Postgres volume was
  fresh (already applied via `docker-entrypoint-initdb.d`) or pre-existing — every migration file
  is written idempotently (`IF NOT EXISTS` / `ON CONFLICT DO NOTHING`), so replaying all of them on
  every boot is safe. This closes a real gap: `docker-entrypoint-initdb.d` only runs against a
  brand-new empty volume, so a developer's existing local Postgres volume would otherwise never see
  `000002` applied by just restarting the container.
- Password hashing: PBKDF2-HMAC-SHA256 (RFC 8018), implemented directly on `crypto/hmac` +
  `crypto/sha256` + `crypto/subtle` — Go standard library only, **zero new `go.mod` dependency**,
  matching this repository's demonstrated minimal-dependency convention (the agent-engine is
  Python-stdlib-only; the control-plane currently has exactly one direct dependency, `pgx`, added
  out of necessity because there is no stdlib Postgres driver). `golang.org/x/crypto/bcrypt` was
  considered and rejected for this reason, not because it's insecure.
- Session tokens: opaque, `crypto/rand`-generated, returned to the caller once; only their
  SHA-256 hash is ever persisted (same "secrets are capabilities, never stored raw" principle
  already applied to the agent-engine's model-provider keys).
- Four HTTP endpoints on the existing control-plane server: `POST /auth/register`,
  `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`.
- `internal/health`'s `NewHandler` becomes `Register(mux, ...)` so `main.go` can mount both the
  health routes and the new auth routes on one `http.ServeMux` — the smallest change that lets two
  route groups share one server, not a framework introduction.

**Out of scope, named for follow-ups (Phases B/C/D/E of the kickoff doc, separate Tracker IDs):**
- No frontend. `apps/console-web` is untouched by this task.
- No agent-engine bridge / Job API — nothing in this task can actually spend a credit yet, only
  grant the signup amount. Debiting credits per generation call is Phase C.
- No team/org/workspace model — deliberately deferred per the kickoff doc's anti-overengineering
  call; a signup is a single `user`, nothing more, until team features are actually requested.
- No payment processor integration — that is a "paid cloud service" decision requiring its own
  explicit founder sign-off when Phase E is reached, not bundled in here.
- No email verification or password-reset flow — noted as an open decision in the kickoff doc;
  the schema does not preclude adding it later.
- No login rate-limiting/lockout — a real hardening item, deferred rather than silently skipped,
  because it needs a shared store (Redis or similar) this project hasn't introduced yet and
  Section 25's anti-overengineering rule says not to add one before a real requirement forces it.

## Acceptance Criteria

- [x] `services/control-plane/migrations/000002_users_auth_billing.{up,down}.sql`: creates/drops
      `users`, `credit_ledger`, `sessions` (+ `pgcrypto` for `gen_random_uuid()`), transactional
      (`BEGIN`/`COMMIT`), idempotent (`IF NOT EXISTS` / `ON CONFLICT DO NOTHING` throughout).
- [x] `services/control-plane/migrations/migrations.go` (new `migrations` package): embeds every
      `*.up.sql` file in its own directory, parses out real statements (skipping the
      transaction-control `BEGIN`/`COMMIT` lines, which are executed as a real Go-managed
      transaction instead), and exposes `Apply(ctx, pool) error`, replaying every migration in
      ascending version order on every call — safe because every migration file is idempotent.
- [x] `services/control-plane/internal/password`: `Hash(plain string) (string, error)` and
      `Verify(encoded, plain string) (bool, error)`, self-describing encoded format
      (`pbkdf2-sha256$<iterations>$<salt>$<key>`), constant-time comparison via `crypto/subtle`.
- [x] `services/control-plane/internal/auth`: `User` (never carries the password hash), `Store`
      interface (the narrow persistence capability — `CreateUser`, `FindUserByEmail`,
      `FindUserByID`, `CreateSession`, `FindUserBySessionToken`, `DeleteSession`), `Hasher`
      interface (so handler tests run fast without paying the real PBKDF2 iteration cost),
      `Deps{Store, Hasher, SessionTTL, SignupCredits, Logger, Clock}`, `Register(mux, Deps)`
      mounting the four routes. Login failure is a generic 401 regardless of whether the email
      exists or the password was wrong (no user enumeration via error message *or* timing — a
      fixed dummy hash is verified on the "email not found" path too). Duplicate email is a typed
      `ErrEmailTaken` surfaced as 409, never a raw database error.
- [x] `services/control-plane/internal/users`: `Store` (pgx-backed), implementing `auth.Store`
      structurally (same pattern as `*pgxpool.Pool` implementing `health.Pinger`). `CreateUser`
      wraps the user insert and the signup credit-grant ledger row in one database transaction —
      a user's `credit_balance` and its ledger history can never disagree.
- [x] `services/control-plane/internal/health/handler.go`: `NewHandler` renamed to
      `Register(mux *http.ServeMux, database Pinger, pingTimeout time.Duration)`; the exact
      `/healthz` / `/readyz` behavior and JSON bodies are unchanged (only the mounting API moved).
- [x] `services/control-plane/internal/config`: new `SessionTTL` (env
      `OMNISTACKAI_SESSION_TTL`, default `720h`) and `SignupCreditGrant` (env
      `OMNISTACKAI_SIGNUP_CREDIT_GRANT`, default `100`) fields, following the exact existing
      `valueOrDefault`/typed-parse pattern.
- [x] `services/control-plane/cmd/control-plane/main.go`: calls `migrations.Apply` right after the
      pool is created (before serving traffic); builds one `http.ServeMux`; registers health and
      auth on it; wires the real `password` package and the real `users.Store` — this is the only
      place the two are connected to the HTTP layer.
- [x] `services/control-plane/Dockerfile`: adds `COPY migrations ./migrations` (required for the
      new `//go:embed` to see its `.sql` files during the container build); image tags unchanged.
- [x] `infra/environments/local/compose.yaml`: mounts `000002_users_auth_billing.up.sql` into
      `docker-entrypoint-initdb.d` alongside `000001` (fast path for a genuinely fresh volume; the
      embedded runner in `main.go` is what makes an *existing* volume correct too).
- [x] `.env.example` + `scripts/env-check.sh`: document and enforce the two new environment names.
- [x] `scripts/test.sh`: a new R-469 block asserting the new contract files exist, the migration
      creates the three new tables, and `go.mod` has not gained a new direct dependency (the
      concrete, checkable proof that password hashing stayed stdlib-only).
- [x] New tests: `migrations_test.go` (pure parsing logic — no real database needed),
      `password_test.go` (round-trip, wrong-password rejection, malformed-hash handling, encoding
      format; the real default iteration count is exercised at least once, faster iteration counts
      cover the rest so `go test` stays fast), `handler_test.go` + `token_test.go` in `internal/auth`
      (an in-memory fake `Store` — register/login/logout/me happy paths, duplicate email, wrong
      password, missing/expired/garbage bearer token, no user enumeration on login failure).
      `internal/users`'s real Postgres-backed `Store` is intentionally **not** unit-tested against
      a live database in `go test` (keeps `control-plane:test` exactly as hermetic as it already
      is — the existing `health` package tests a fake `Pinger` for the same reason); it is
      exercised for real by this task's live manual smoke test instead (see Gates below).
- [x] `task verify` stays green (control-plane's `lint`/`test`/`build` steps already run inside it).
- [x] Manual live smoke: real `docker compose up` (Postgres + control-plane), real HTTP register →
      login → me → logout → me-after-logout round trip against the actual running container.
