# R-468: Multi-turn chat / "continue editing this app" in the Studio

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-17
**Completed:** 2026-09-17

## Objective

R-467 wired the hybrid engine into the Studio's build-time toggle, but every `/api/build` call is still a
fresh, stateless one-shot prompt — there is no way to say "now add a favorites feature to the app I just
built" and have it apply as a further edit to the same repo. Two rounds of direct-code investigation
confirmed: no session/conversation concept exists anywhere in this repo (`StudioBuildHistory` is an
unrelated "recent builds" list, never wired to any edit primitive); the apply/commit half already works,
tested, unmodified (`edit/diff.py::plan_edit` → `assemble_project` + `diff_projects`, generic over any two
`ApplicationIR`s; `edit/apply.py::commit_edit` → `apply_diff` + `git_service.commit_all`, proven end-to-end
by `tests/test_edit_loop.py::CommitEditTests::test_commit_edit_records_a_second_commit`); the missing half
is producing IR #2 — `generate_ir` takes only a single fresh prompt, no code merges two IRs today.

`solution_packs/ai_delta.py` + `solution_packs/application.py:196-244` already prove the right shape: the
model proposes a small, strictly bounded, validated delta (new entities/apis/screens only — never asked to
restate the whole app), merged onto the base IR by tuple concatenation (`base_ir.entities +
proposal.entities` via `dataclasses.replace`), pre-checked for name/path/id collisions, backstopped by
`ApplicationIR.__post_init__`'s own uniqueness validation and a final `validate_ir`/`has_errors` semantic
check. That merge is generic; only its current caller and `AIDeltaProposal` itself are pack-coupled
(mandatory `pack_id`/`pack_version`/`base_ir_sha256`). Re-calling `generate_ir` with an augmented prompt and
diffing old vs new was rejected: no code, no test, and no guarantee the model preserves every existing
entity/screen verbatim (the system prompt actively says to "replace the template content") — a supersetting
failure there would produce a huge, confusing diff, the opposite of the clean incremental history this
feature exists for.

So: a new, generic sibling to `ai_delta.py` (`intake/app_delta.py`) that any `ApplicationIR` can use, new
Studio session state to track the current IR + turn history per build, one new HTTP endpoint pair, and a
small chat box in `page.py`.

## Scope (v1)

**In scope:** additive follow-up turns only — new entities/relations, new API endpoints, new screens (on
existing or new entities). A single Studio session per running server process, in-memory only, bounded, lost
on restart (same idiom as `StudioBuildHistory`/`StudioPreviewManager`). Works for plain-prompt builds and
single-surface Ecosystem Pack builds (both produce exactly one `ApplicationIR` + one repo).

**Out of scope, named for follow-ups:**
- Renaming/modifying/removing existing entities/fields via chat (collisions are rejected, never merged).
- Multi-surface ("all surfaces") ecosystem builds and Solution Pack builds — Solution Pack apps already have
  their own, separate AI-delta path (`ai_features`/`ai_delta_prompt`) at initial-build time; `/edit` returns
  a clear, honest error for these rather than silently ignoring or guessing.
- Wiring R-466's `compile_and_repair` into the edit flow (needs the toolchain) — deferred.
- Undo/revert UI (the git history exists on disk; no UI exposes `git log`/`git revert` yet).

## Live discovery (found while implementing, not anticipated in the contract)

Building the end-to-end test surfaced a genuine gap in the delta schema mirrored from `ai_delta.py`:
neither module validated that a proposed screen's `role` refers to one of the base IR's *actual* declared
roles — only that it's a well-formed lower_snake_case identifier. `ApplicationIR.__post_init__` does catch
an invalid role as a last resort (it did, in the first failing test run: "screen 'favorites_list'
references unknown role 'reader'" — the ecosystem's "author-studio" surface only declares an `author` role,
unlike `minimal-blog`'s `author`+`reader`), but only *after* `generate_app_delta_proposal` had already
returned successfully, past the point where a rejection could be fed back for a retry. Fixed by adding an
explicit role-existence check to `parse_app_delta_proposal` (so a bad role is caught at the same layer as
every other base-IR collision, and gets the retry-with-feedback benefit) and to `apply_app_delta` (defense
in depth, matching the existing pattern), plus listing the app's real roles in the prompt so the model has
the information to avoid the mistake in the first place. New tests cover both the parse-time rejection and
the merge-time defense-in-depth check.
