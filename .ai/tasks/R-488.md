# R-488: Runtime — real Daytona driver

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-19
**Completed:** 2026-09-19

## Objective

Third of the five-task sandbox-provider sequence (R-486..R-490). E2B (R-486) and Vercel Sandbox
(R-487) each proved `SandboxLifecycleProvider`/`sandbox_http.py` generalize across differently-
shaped APIs; this task adds Daytona — notable because its documented default isolation is **plain
Docker containers** (weaker than E2B/Vercel's Firecracker microVMs), a real tradeoff worth
surfacing honestly, and because its API shape differs from both prior drivers in a third way: the
create response carries no URL at all.

## Design (verified against real, current Daytona documentation before writing any code)

- **A genuinely different API shape from both prior drivers**: E2B returns a URL pattern to build
  in the create response; Vercel returns a full `routes[]` array with real URLs in the create
  response; **Daytona's create response returns neither** — only sandbox metadata (`id`, `state`,
  ...). Getting a usable URL requires a **second, separate call**:
  `GET /sandbox/{id}/ports/{port}/preview-url` → `{"url": ..., "token": ...}`. `create()` therefore
  makes two real HTTP requests, not one — documented here explicitly since it's a meaningfully
  different shape the `SandboxLifecycleProvider` contract still accommodates cleanly (`create()`
  returns one `SandboxHandle`; nothing in the contract assumes one HTTP call per method).
- **Auth token requirement**: a preview URL normally needs a per-request `X-Daytona-Preview-Token`
  (or a signed URL with the token embedded) *unless* the sandbox was created with `"public": true`,
  in which case the preview link is publicly accessible with no token at all (confirmed directly
  from `daytona.io/docs/en/preview/`). Since `SandboxHandle.url` is a single string with no room
  for a companion auth header, `create()` always requests `"public": true` — the only way this
  contract's single-URL shape can produce something a plain iframe/browser can load directly,
  matching what this platform's Studio preview already does for every other provider.
- **Endpoints verified from Daytona's own docs** (fetched directly; a real base-URL ambiguity was
  found across their own doc pages — `app.daytona.io/api/sandbox/...` appears in one search
  result, `api.daytona.io/sandbox/...` in a more detailed, schema-bearing page fetched directly —
  resolved the same way R-486's E2B v1/v2 ambiguity was: prefer the more specific, structured,
  directly-fetched source and note the ambiguity honestly rather than silently picking one):
  `POST https://api.daytona.io/sandbox` (create), `GET https://api.daytona.io/sandbox/{id}` (get),
  `DELETE https://api.daytona.io/sandbox/{id}` (delete), `GET
  https://api.daytona.io/sandbox/{id}/ports/{port}/preview-url` (the real URL for a given port).
  `Authorization: Bearer <DAYTONA_API_KEY>` (the existing `RUNTIME_SPECS["daytona"]` key, declared
  since an earlier task, unused until now).
- **Minimal create request body**: only `{"public": true}` plus a generated `labels` tag — every
  other documented field (`snapshot`, `target`, `cpu`, `memory`, `disk`, ...) has a real, confirmed
  platform default (Daytona's own docs: "use the Daytona default snapshot" when `snapshot` is
  omitted; the SDK's own params all default sensibly), so this task does not guess values for
  fields whose exact required/optional status wasn't independently confirmable from the fetched
  pages — the same conservative approach R-486 took for E2B's `templateID` default.
- **A real, honest isolation-strength tradeoff, surfaced not glossed over**: Daytona's *default*
  sandbox isolation is plain Docker containers (shared kernel) — weaker than E2B/Vercel's
  Firecracker microVMs (confirmed by this sequence's original R-486 research: "Daytona: Default —
  plain Docker containers... Kata/Sysbox available but opt-in"). This driver does not attempt to
  select the stronger opt-in isolation mode (undocumented in the pages fetched for this task);
  worth calling out explicitly once R-490's provider-selection surface exists, so this tradeoff is
  visible to whoever picks a provider, not silently hidden.
- **New `runtime/daytona.py`: `DaytonaSandboxProvider`**, implementing `SandboxLifecycleProvider`
  via the same shared `sandbox_http.py` from R-486, unchanged — the third proof this helper
  generalizes.
- **No real credentials exist in this environment** (`DAYTONA_API_KEY` unset) — every gate is
  offline via the same injected-fake-opener pattern established in R-486/R-487; live-cloud
  verification is honestly deferred.

## Gates & Evidence

**Daytona's real REST API was verified directly** (fetched multiple `daytona.io`/mirror doc pages,
not assumed from training data). **A real base-URL ambiguity was found across Daytona's own
documentation** (the same kind of inconsistency R-486 hit with E2B's v1/v2 paths): a web-search
snippet showed `app.daytona.io/api/sandbox/...`, while a more detailed, schema-bearing page fetched
directly showed `https://api.daytona.io/sandbox` with exact request/response field names. Resolved
the same way: preferred the more specific, structured, directly-fetched source
(`api.daytona.io/sandbox`) consistently for every endpoint, documented in the code and here rather
than silently guessing.

**A third, genuinely different API shape confirmed and correctly handled**: unlike E2B (URL
pattern) and Vercel (`routes[]` in the create response), Daytona's `POST /sandbox` response carries
**no URL at all** — only `id`/`state`. `create()` therefore makes a real second HTTP call,
`GET /sandbox/{id}/ports/{port}/preview-url`, verified by a dedicated test
(`test_create_makes_two_calls_and_returns_the_real_preview_url`) asserting both requests' exact
URLs, methods, and that the create call happens strictly before the preview-url call (and that a
sandbox-id-omitted create response never reaches the second call at all — verified by
`test_create_raises_when_the_provider_omits_a_sandbox_id` asserting exactly one request was made).

**The `public: true` requirement, confirmed and applied**: Daytona's own docs state a non-public
sandbox's preview link needs a companion `X-Daytona-Preview-Token` header; since
`SandboxHandle.url` is a single string with no room for a companion header, `create()` always sets
`"public": true` so the returned URL works with a plain, unauthenticated fetch — verified by
asserting `create_body["public"] is True` in the request test.

**A real, honest isolation-strength tradeoff, surfaced not hidden**: Daytona's documented default
sandbox isolation is plain Docker containers (shared kernel) — weaker than E2B/Vercel's Firecracker
microVMs, per this sequence's own R-486 research. This driver does not attempt to select Daytona's
opt-in stronger isolation modes (undocumented in the pages fetched for this task); called out
explicitly here and in the code so it stays visible once R-490's provider-selection surface exists,
rather than silently treating all three providers as equivalent.

**No real `DAYTONA_API_KEY` exists in this environment** (`.env` checked: absent). Every test is
offline via the same injected-fake-opener pattern established in R-486/R-487 — the third proof
`sandbox_http.py` generalizes across a third, differently-shaped provider API. Real live-cloud
