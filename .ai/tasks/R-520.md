# R-520: Multi-app preview for template projects (Phase T, T-2)

**Phase:** Phase T (Template Marketplace)
**Status:** COMPLETED
**Started:** 2026-09-21
**Completed:** 2026-09-21

## Objective

A template project is several apps sharing one API and one database (for example a rider web app,
a driver PWA, an admin panel and the API). The Preview tab must run all of them and let the user
switch between them. Mobile apps (PWA) show in a phone frame, and the demo logins sit next to the
preview. The prompt-built preview path stays exactly as it is.

## Design

### Project runtime manifest: `omnistack.json`

"Use template" now also writes `omnistack.json` at the root of the user's copy. It holds
schema_version, name, the template {slug, version}, apps, roles and demo users, and it is part of
the first commit. The project describes itself, so the user owns it and later edits can add an app.
Template authors must not ship their own `omnistack.json` (reserved name). A repo without
`omnistack.json` keeps the existing single-app preview.

### Runtime contract for template apps (documented in `templates/catalog/README.md`)

- Every app directory has a `package.json` with a `dev` script. The platform runs `pnpm run dev`.
- Env for every app: `PORT`. For `api`: `DATABASE_URL`, `JWT_SECRET` (random per preview) and
  `GET /health` answering 200. For `web`/`admin`/`pwa` (Next.js): `BASE_PATH` (to use as Next
  `basePath`), `API_URL` (internal, for server-side calls) and `NEXT_PUBLIC_API_URL` (the proxied
  path, for browser calls).
- Database: a fresh per-project database. The API app's `migrations/*.sql` then `seed/*.sql` are
  applied in name order.
- Dependencies: one `pnpm install` at the repo root when `pnpm-workspace.yaml` exists, otherwise one
  per app.

### Agent-engine

- `localrun/multiapp.py` (new; `plan.py`/`run.py` untouched):
  - `load_project_manifest` and a pure `build_multiapp_plan`: ports, base paths
    `/preview/<project>/<app>`, env, database steps and install steps.
  - `MultiAppSession`: each app runs in its own process group, and stop kills the whole group, so
    no orphaned `next dev` children are left.
  - `start_multiapp`: setup steps, launch, then per-app readiness.
  - App processes get a **minimal environment** (PATH/HOME/locale plus their own variables), never
    the Studio's model keys.
- `studio/preview.py`: template workspaces start **asynchronously** in a background thread. POST
  returns `starting` at once and status reports phase, per-app readiness, `apps[]` and
  `demo_users[]`. Stop cancels an in-flight start.
- `studio/templates.py`: writes `omnistack.json`, and the validator reserves the name.

### Console

- The `/preview/<project>/…` proxy routes `/<appId>/…` to that app. The full path is kept because
  the app runs under that `basePath`, so no HTML rewriting is needed. `/api/…` goes to the API with
  the prefix stripped. Loopback-only targets are kept. Single-app previews behave exactly as
  before.
- `studio-preview.tsx`:
  - polls while starting and shows the phase;
  - app switcher (hidden for single-app previews);
  - PWA apps default to a phone frame;
  - "Demo logins" panel with copy buttons;
  - link to the API health check.

### Not in this task

WebSocket HMR through the proxy (a page reload shows code changes), native mobile, public preview
URLs, and the real templates themselves (T-6+).

- `test_localrun_multiapp` (17), `test_studio_preview_multiapp` (8) and `test_studio_templates`
