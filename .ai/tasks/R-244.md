# R-244 — Sub-collection route wiring (parent-scoped lists)

## Requirement

Clear the main class of remaining `501` stubs (Brief §9/§27/§34): wire the sub-collection GET pattern
`GET /<parents>/{parentId}/<children>` to a parent-scoped list. The child entity (the endpoint's
`response_schema`) must be a repository entity with **exactly one** foreign-key relation (many_to_one /
one_to_one); the endpoint lists that entity filtered by the relation's FK column = the path parameter.
Endpoints that do not match (no entity, not exactly one FK relation, multi-param) stay labelled `501`.
Deterministic and offline; nothing runs. Seed/fixture data is deferred (the IR carries no seed values to
emit honestly). Committed directly to `main` (R-244).

## Acceptance criteria

- `wire_endpoint` recognizes `GET /<parents>/{parentId}/<children>` as `LIST_BY` when the response
  entity is a repo entity with exactly one many_to_one/one_to_one relation; otherwise `None`.
- Data-access emits a filtered list per FK relation: Python `list_<table>_by_<rel>(<rel>_id)`, Go
  `List<Entity>By<Rel>(ctx, db, <rel>Id, limit)`, filtering `WHERE <rel>_id = <param>` (value
  parameterized, column a fixed IR-derived identifier).
- Python routers call the filtered list (valid Python); Go handlers call the store function.
- Non-matching sub-collection endpoints stay `501`; byte-stable; nothing runs.
- Offline tests cover the LIST_BY mapping + None cases, filtered-list emission, and Python/Go wiring.

## Design notes

- `route_wiring.py`: add `Op.LIST_BY`, a `relation` field on `Wiring`, `fk_relations(ir)` helper, and a
  `fk_by_entity` argument to `wire_endpoint` for the LIST_BY branch (single-FK child only).
- `data_access.py`: emit `list_<table>_by_<rel>` (Python) / `List<Entity>By<Rel>` (Go) for each FK
  relation of an entity.
- `backend_python.py` / `backend_go.py`: pass the FK map to `wire_endpoint`; render the LIST_BY body
  (Python: `await <table>.list_<table>_by_<rel>(<param>)`; Go: `store.List<Entity>By<Rel>(...)`).

## Model and cost trace

Deterministic; no model call, no network, no DB connection, no handler executed. cloud_calls zero.
