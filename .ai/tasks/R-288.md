# R-288 — Deduplicated In-Flight Generated Mutation Requests

**Status:** in_progress
**Phase:** BASIC/MVP — Founder Stage 0
**Branch:** `main`
**Complexity:** L2 (deterministic codegen)

## Objective

R-280/R-286/R-287 made all three generated data-*fetch* paths (LIST, LIST_BY, detail GET) race-safe.
Writes are still unguarded: `useCreate<Entity>`, `useUpdate<Entity>`, and `useDelete<Entity>` track
`loading` but do not prevent a second invocation while one is in flight, so a double-clicked
Create/Save/Delete (or a programmatic re-call) fires a duplicate POST/PUT/DELETE — a data-integrity bug
(duplicate records, double deletes) worse than a stale read. R-288 dedupes concurrent mutation calls: a
mutate call while a request is pending returns the pending promise instead of starting a second request.

## Requirement

In `nextjs.py` `_hooks_file`, the `# 3/4/5` mutation-hook blocks, add an in-flight dedupe using a
`pendingRef`:

- `const pendingRef = useRef<Promise<T> | null>(null);` (T = `<Entity>` for create/update, `void` for
  delete). `useRef` is already imported (R-280).
- The callback's first statement: `if (pendingRef.current) return pendingRef.current;`.
- Run the existing try/catch/finally body inside an IIFE captured as `pendingRef.current = request;` and
  `return request;`. The `finally` keeps `setLoading(false)` and adds `pendingRef.current = null;`.
- Keep the underlying `api.create|update|delete<Entity>(...)` call, the callback signature, and the
  return shape (`{ create|update|remove, mutate, loading, error, reset }`) unchanged.

Do not touch the fetch hooks, the generated API client, backend, or IR. Deterministic and
description-only-stable.

## Acceptance criteria

1. Each mutation hook emits `const pendingRef = useRef<Promise<…> | null>(null);` and
   `if (pendingRef.current) return pendingRef.current;` as the first callback statement.
2. The body runs in an IIFE assigned to `pendingRef.current` and returned; `finally` sets
   `setLoading(false)` and `pendingRef.current = null;`.
3. The `api.create/update/delete<Entity>(...)` call and the return shape are unchanged; errors still set
   error state and reject.
4. Fetch hooks and the API client are untouched; description-only IR changes remain byte-identical.
5. Focused tests + `test_nextjs_hooks` + full offline gates + both demos pass.

## Design notes

- Dedupe (return the pending promise) is preferred over throwing: a double-click resolves once, no
  duplicate request, and the `Promise<Entity>` return type is preserved.
- Existing `test_nextjs_hooks.py` mutation assertions (`return await api.createPost(data, options);`, the
  return-shape lines, etc.) remain valid substrings — expected to pass unchanged.

## Model and cost trace

Deterministic; no model call, no network, no DB. local_calls 0 / cloud_calls 0.
