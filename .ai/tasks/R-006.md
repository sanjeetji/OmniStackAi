# R-006 — Loopback-only Ollama ModelProvider adapter

## Requirement

Implement the first production adapter behind the accepted Python `ModelProvider` boundary. The
adapter uses Ollama's native loopback API for health, discovery, chat generation, and NDJSON
streaming while keeping provider details out of product/domain logic.

The supplied tracker omits R-006 through R-009. This task is reconstructed from Brief Sections
18.3, 75, 84, 85, 91, and 92 with the founder's standing instruction to continue one Tracker ID
at a time.

## Acceptance criteria

- `OllamaProvider` is runtime-substitutable for `ModelProvider` and exposes stable provider ID
  `ollama-local`.
- Only `http://127.0.0.1:11434` and `http://localhost:11434` are accepted during Stage 0, and HTTP
  redirects are rejected.
- Version health, pulled-model discovery, non-streaming chat, and NDJSON streaming are mapped into
  vendor-neutral records with deterministic ordering and stable platform-owned errors.
- Network calls have explicit timeouts, bounded bodies/lines, bounded concurrency, and observable
  cancellation; server error bodies and raw network details are not exposed.
- Model capabilities and context/output budgets come from explicit conservative profiles; model
  names alone never produce verified capability claims.
- Standard-library tests cover successful conformance and malformed, HTTP, timeout, oversized,
  endpoint, concurrency, cancellation, and incomplete-stream failures.
- An opt-in live command proves health, discovery, generation, and streaming on local Ollama, while
  the repository's static verification remains independent of runtime availability.
- No provider SDK/dependency, cloud provider/call, routing/fallback, service process, database or
  Compose change, infrastructure, or native/device work is added.
