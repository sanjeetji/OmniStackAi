## This task: `services/api`, the database and the demo data

**Domain**

- **Roles:** rider, driver, admin. JWT access token (15 min, HS256 via `node:crypto`), rotating
  refresh tokens (hashed, revocable), and scrypt password hashes. Phone OTP goes through a mock SMS
  provider: the code is logged, and `123456` is accepted only while `OMNISTACK_PREVIEW=1`.
- **Trip state machine:** `requested → driver_assigned → driver_arrived → in_progress → completed`,
  plus `cancelled` (rider, driver or admin, with a reason) and `no_driver`. Each transition checks
  who may make it and writes a `trip_events` row. The ride starts only with the rider's 4-digit PIN.
- **Dispatch:** the nearest approved, online, idle drivers of the requested vehicle type within
  5 km get one offer at a time. An offer expires after 20 s and passes to the next driver. After 5
  attempts the trip becomes `no_driver`. Demo "simulated" drivers accept automatically and drive
  (`DEMO_SIMULATION=1`, on in preview), so a single rider can see a full trip. A real driver
  signed into the driver app is always offered first.
- **Fares:** `max(min_fare, base + per_km × km + per_min × min) × surge + booking fee − promo`.
  Distance comes from the mock maps provider (haversine × 1.3 road factor, 22 km/h city speed).
  Surge comes from the zone containing the pickup.
- **Money:**
  - A double-entry-style wallet ledger: every movement is a `wallet_transactions` row with its
    balance-after.
  - Rider top-up goes through a mock card payment intent (the Stripe/Razorpay-shaped interface;
    a live provider can plug in).
  - A completed trip debits the rider (wallet) or records cash, credits the driver net of
    commission, and books the commission.
  - Refunds (admin), payout requests (driver) and "mark paid" (admin) are included.
- **Realtime:** Server-Sent Events at `GET /stream?token=`. Events: `trip.updated`, `offer.new`,
  `offer.closed`, `driver.location`, `wallet.updated`, `notification`, `admin.live`.
- **Also:** ratings (both ways, tags), promo codes (percent or flat, caps, limits, expiry), saved
  places, notifications, support tickets with message threads, audit log for admin actions,
  OpenAPI document at `/openapi.json`, and `/health` (checks the DB).

**Data**

- `migrations/001…005` (core, fleet, trips, money, support).
- `seed/001_demo.sql`, generated deterministically by `scripts/generate-seed.mjs` (shipped, so
  users can regenerate). It has:
  - 3 demo logins (rider, driver, admin);
  - 48 riders and 32 drivers across 5 vehicle types, 8 of them simulated and online around the
    city;
  - 30 Bengaluru places, 6 surge zones and 6 promo codes;
  - about 420 historical trips over 30 days with events, ratings and matching ledger entries;
  - tickets, notifications and payouts.

**Tests** (`services/api/test`, `node --test`)

- Pure unit tests: fare, geo, trip state machine, JWT, passwords, dispatch ranking and promo
  rules. They are run offline by the agent-engine test suite (`node` is already required).
- A workflow test run live against a real database (skipped without `DATABASE_URL`): register →
  top up → estimate → book → simulated driver accepts → arrive → start with PIN → complete →
  wallet debited, driver credited, commission booked → rate → admin dashboard reflects it.

## Gates & Evidence (real runs, 2026-09-21/22)

- `tsc --noEmit` (TypeScript 5.9.2, strict, `erasableSyntaxOnly`): exit 0 over every source.
- Unit tests: **20/20**. They found a real rounding bug (`money(1.005)` gave 1.00 because of binary
  floating point), fixed with decimal-string shifting.
- Seed: two runs give an identical sha256.
- On a fresh database in the platform Postgres: all 5 migrations and the seed load.
  - 0 ledger rows with a wrong running balance, 0 wallets differing from their ledger.
  - Every completed trip's money nets to zero, and 0 negative rider wallets.
  - Trips: 352 completed, 54 cancelled, 24 no-driver.
- The live API against that database (simulation on) passed the workflow **4/4**:
  - Health and OpenAPI.
  - A new rider signs up (₹100 welcome), tops up (a declined test card handled), and WELCOME50
    applies. The rider books; a second booking is refused (`active_trip`). A simulated driver
    completes the trip in about 47 s with exactly the expected events, and the wallet settles to
    the paise. Rating works, and a second rating gets 409.
  - The real demo driver gets the offer first and never sees the PIN; a wrong PIN is refused. On
    a cash trip the driver's wallet shows exactly `−commission`, and the trip ledger nets to 0.
    The rider's SSE stream saw assigned, in progress and completed.
  - Admin: the 14-day dashboard reflects today's trips, a refund returns the exact fare (a second
    refund gets 400), the audit entry is written, and riders get 403 and anonymous callers 401.
  - The API log showed no errors. The scratch database was dropped afterwards.
- `task verify`: 3,971 OK (3 new), 0 model calls. `task lint`, `security:quick` (secret policy
  passed with the demo hashes in the seed), `env:check`: exit 0. `scripts/test.sh` R-526 block
  passed.
