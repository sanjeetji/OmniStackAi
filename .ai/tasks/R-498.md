## Objective

The founder tested the console from `172.28.64.242:4321` (build 7, "Simple CRM") and listed what a
platform still needs: working preview, Publish, Git, domains, Skills, General, SEO, Connectors,
payments, AI usage, Logs, SQL editor, Secrets, DB explorer, Analytics, chat attachments/stop/audio,
Configuration/Security/Tests, model configuration, multiple projects. They asked for (a) an
overview and a build/don't-build decision per feature, (b) an implementable spec per task so work
can pause and resume, (c) an explanation of why running the platform needs two different commands,
and (d) one shell script to run everything.

This task delivers all four. It writes no feature code: it produces the plan and the runtime
tooling that every following task uses.

## What was verified first (not assumed)

- `localrun/run.py` binds generated apps to `127.0.0.1:<free port>` — the preview URL is loopback.
- `studio/history.py` is in-memory with a size cap; `studio/session.py` holds the editable IR in
  RAM. **Live proof:** after restarting the Studio, build 7 returned `{"turns": []}` and `404` for
  its files, and the next build was numbered `1` again.
- Preview mode itself works: a real build (30 s) then `POST …/preview` returned
  `{"status":"ready","web_url":"http://127.0.0.1:59570"}` in **5 s**, and fetching that URL
  returned **200, 41,338 bytes, `<title>Simple Note Taking</title>`**. So "Preview is not working"
  was the Studio running in build-only mode, not a broken feature.
- Control-plane schema is `users`, `credit_ledger`, `sessions` (migrations 000001–000003) — no
  projects table, so nothing per-project can exist yet.
- Preview already creates a real per-app PostgreSQL and applies the generated migrations, so a
  database explorer can be honest rather than mocked.
- Every build is already a real git repository with one commit per build/edit — only the remote,
  the token and the UI are missing.

## Gates & Evidence

**Script, tested for real, and two genuine bugs found and fixed in my own code:**

1. `down` silently skipped stopping the containers. Cause: `[[ -n "$who" ]] && warn …` was the
   last command in a loop body, so when both ports were free the loop's exit status was 1 and
   `set -e` aborted the function. Verified by `docker ps` still showing the containers up.
   Replaced with an `if`.
2. It still aborted: `port_listener` ends in a pipeline whose first command is `lsof`, which
   exits **1 when nothing is listening**, and the script runs with `pipefail`. So "the port is
   free" propagated a failure into `who="$(port_listener …)"`. Fixed with a guarded
   `{ lsof … || true; }`, and the same guard applied to the two `ps` pipelines in `stop_service`.

**After the fixes:** `down` stops the processes *and* the containers and exits 0 (`docker ps`
empty). A **cold `up` from nothing took 13.8 s** and reported control-plane healthy on :8080,
studio on :4173 in **preview** mode, console on :4321, plus the machine's LAN address and an
honest note that a generated app's preview is still loopback-only until F-02. `status` reports
every component with its port, pid and the **authoritative** Studio mode (probing
`/api/preview`: 200 = preview, 404 = build-only) — the first version guessed from the log and
reported "build-only?" while preview mode was actually live; that heuristic was replaced.
`logs console` tails the real Next.js output. End-to-end after the restart cycle: login 200,
`/` 200, `/studio` 200, `/settings` 200, `/api/preview` 200.
