# R-486: Runtime — real sandbox lifecycle contract + E2B driver

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-19
**Completed:** 2026-09-19

## Objective

First of a five-task sequence toward the founder's per-user isolation direction. Confirmed via
research before any code: every serious 2025-2026 AI app-builder platform running real server-side
code (not just browser-only sandboxing) uses a **managed microVM/gVisor sandbox provider** — self-
hosting Firecracker/Kata/K8s multi-tenancy from scratch is a multi-quarter platform-engineering
effort this project doesn't have headcount for. The founder's explicit direction (after seeing this
research): build real, pluggable drivers for **multiple** providers (E2B, Vercel Sandbox, Daytona)
so they can be switched later by cost/speed/smoothness, plus a free local-browser option — this
task is the first: prove the pattern end-to-end with one real provider (E2B) before repeating it.

## Design (verified against real, current provider documentation before writing any code)

- **The existing `RuntimeProvider`/`PreviewPlan` abstraction (`runtime/contracts.py`) is a pure
  *planner*, not a real orchestrator — confirmed by direct read.** `preview_plan()` returns a
  description of local install/run commands plus a URL string; executing it is a separate step
  (`local.run_preview`) that runs those commands **on the same machine**. The existing
  `CloudSandboxProvider` (`runtime/drivers.py`) stub reuses this exact shape with a **hardcoded
  placeholder URL** (`https://<id>.e2b.dev`) — it never actually calls any provider's API. This
  planning abstraction is right for local execution and stays completely untouched; it cannot
  become "real" for a cloud sandbox by filling in a stub, because a real cloud sandbox needs actual
  request/response lifecycle (create → get a real ID/URL → later kill it), which the pure-planning
  shape has no room for.
- **New, additive `SandboxHandle` + `SandboxLifecycleProvider` (`runtime/contracts.py`)**: a
  `SandboxHandle` (`provider_id`, `sandbox_id`, `url`, `status`) and a Protocol with `create()`,
  `status()`, `kill()` — genuinely mirroring what a real cloud sandbox needs, alongside (not
  replacing) the existing `RuntimeProvider`.
- **New `runtime/sandbox_http.py`**: a small, safe, stdlib-only JSON HTTP helper shared by every
  sandbox driver this sequence adds (E2B now; Vercel Sandbox/Daytona in R-487/R-488) — bounded
  response size, finite timeout, redirect rejection (never replay an auth header to another host),
  and stable typed error mapping, at a much smaller scale than `model_gateway/cloud.py`'s own
  (that file is LLM-completion-specific — streaming, retry-after pacing, finish-reason mapping —
  none of which a sandbox lifecycle call needs; this is a new, appropriately-scoped module, not a
  copy-paste of it).
- **New `runtime/e2b.py`: `E2BSandboxProvider`**, implementing `SandboxLifecycleProvider` for real,
  verified against E2B's actual documented REST API (fetched directly from `docs.e2b.dev`, not
  assumed from training data):
  - `POST https://api.e2b.app/sandboxes` with `{"templateID": ..., "timeout": ...}`, header
    `X-API-Key: <key>` → `201` with `sandboxID` in the body.
  - Public URL construction: `https://{port}-{sandboxID}.e2b.app` (E2B's own documented pattern).
  - `DELETE https://api.e2b.app/sandboxes/{sandboxID}`, same header → `204` on success.
  - `templateID` defaults to E2B's own documented generic default (`"base"`), overridable via a new
    `E2B_TEMPLATE_ID` env var — a real generated OmniStackAI app needs a custom template with the
    right toolchain pre-installed, which is a separate, later concern once a real account exists to
    build one against; this task proves the lifecycle itself, not a production-ready template.
  - Activated by `RUNTIME_SPECS["e2b"]`'s existing `E2B_API_KEY` env var (already declared, unused
    until now) — same "add a key, it activates" pattern as every cloud LLM provider.
- **No real API key exists in this environment** (`.env`/`.env.example` checked: `E2B_API_KEY=` is
  present as a name-only placeholder, no value) — every automated test is offline (a fake HTTP
  transport injected the same way `cloud.py`'s adapters already support an injectable `opener`),
  and the real live-cloud call is honestly marked pending a real key from the founder, not faked.
- **Not in scope for this task**: wiring `E2BSandboxProvider` into the Studio's preview flow
  (`studio/preview.py`) or `_build_stream()` — this task proves the driver is real and correctly
  built against E2B's actual API; swapping what the Studio actually uses for preview is a separate,
  later decision once more than one provider exists to choose between (R-490's job).

## Gates & Evidence

**E2B's real REST API was verified directly** (fetched `docs.e2b.dev` pages, not assumed from
training data) before writing `e2b.py`: `POST https://api.e2b.app/sandboxes` (`X-API-Key` header,
`{"templateID", "timeout"}` body, `201` response with `sandboxID`), public URL pattern
`https://{port}-{sandboxID}.e2b.app`, `DELETE https://api.e2b.app/sandboxes/{sandboxID}` → `204`.
The `GET /sandboxes/{id}` status response's exact field shape was **not** independently verifiable
from the fetched pages — `E2BSandboxProvider.status()` defensively looks for a `"state"` string
field and falls back to keeping the handle's existing status when absent, documented as an honest
gap in the code's own comment rather than a guessed-and-hidden assumption.

**Target→port mapping reused, not duplicated**: `_port_for_target()` calls the existing
`LocalRuntimeProvider().preview_plan(app_dir, target)` and parses the port out of its returned
`http://127.0.0.1:{port}` URL — the single source of truth for this mapping stays in `local.py`;
an unsupported target raises the same `UnsupportedRuntimeTargetError` the local provider already
raises, verified by a new test the exercises all four known targets (`nextjs-web`→3000,
`nextjs-admin`→3001, `backend-python`→8000, `backend-go`→8080) plus the unsupported-target case.

**No real `E2B_API_KEY` exists in this environment** (`.env` checked: absent; `.env.example` has
only the pre-existing name-only placeholder). Every test is offline via an injected fake
`OpenerDirector`-shaped object (mirroring `model_gateway/cloud.py`'s own testable-opener pattern) —
**live-cloud verification against a real E2B account is honestly not possible here and is not
claimed**; it is deferred to whenever the founder provides a real key, exactly like this project's
existing precedent for cloud LLM providers (e.g. Groq/Anthropic stay unverified-live until a real
key is added, and `task verify` never depends on one).

**agent-engine `task verify`**: `3,680 tests OK` (22 new: 9 in `test_runtime_sandbox_http.py`, 13
in `test_runtime_e2b.py`), 0 model/network calls. New tests cover: successful create/kill/status
against hand-built E2B-shaped responses; a missing key raising before any request is sent (both
`create()` and `kill()`); HTTP error mapping (401 with a real E2B-shaped `{"message",
"error_code"}` body, and a non-JSON 500 body falling back to a generic message); oversized/
