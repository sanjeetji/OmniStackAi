## Design

- **Preview start is synchronous** (`StudioPreviewManager.replace()`/`.restart()` block until
  ready, errored, or unavailable — confirmed live during R-478). There is no server-side "starting"
  state to poll for; the only "starting" phase visible to the client is the in-flight
  `POST /jobs/build/{id}/preview` itself. So polling's real job is **crash detection**, not
  progress-watching: a 5s `setInterval` while `status.status === "ready"` (cleared on unmount/any
  other status), calling `GET /jobs/preview`, since `status()` lazily notices a subprocess that
  died on its own (`_refresh_locked`).
- New `apps/console-web/app/studio/studio-preview.tsx`: owns `status: PreviewStatus | null`,
  `starting: boolean`, `elapsedMs: number`, `disabled: boolean` (build-only mode), `fetchError`.
  One effect triggers `POST /jobs/build/{buildId}/preview` whenever `buildId` changes to a real
  value **or** `previewVersion` (a counter bumped by the parent after every successful edit —
  `_edit()` never restarts the preview on its own, unlike `_build()`, so this task's own re-preview
  call is what keeps the iframe fresh) changes. A second effect runs the 5s crash-detection poll.
  A third ticks `elapsedMs` while `starting` so the spinner shows real elapsed time (cold starts
  confirmed live up to ~45s during R-478).
- **Verified response shapes, not assumed** — every `StudioPreviewManager` status dict read
  directly from `preview.py` before writing `PreviewStatus`: `{"status": "idle"|"stopped", message}`
  (idle/stopped/exited), `{"status": "error"|"unavailable", message}` (start failed / no web
  target), `{"status": "ready", web_url, message, api_url?}`. The build-scoped route's own
  additional `{"status": "error", "message": "That build is no longer available..."}` case
  (confirmed live in R-478) renders through the same "error" branch, showing the agent-engine's
  real message — not a generic failure.
- **Degradation when disabled**: a 404 from either `POST /jobs/build/{id}/preview` or
  `GET /jobs/preview` sets `disabled` and renders a static message ("Live preview isn't running —
  start it with `task agent-engine:studio:preview`") instead of a broken iframe.
- **Manual controls**: a small header (Restart via `RefreshIcon`, Stop via `StopIcon` — both icons
  already existed unused since R-475, purpose-built for this) shown whenever a preview has been
  started for this build — real controls over the real R-478 routes, not placeholders.
- New `lib/control-plane.ts` additions: `PreviewStatus` type, `getPreviewStatus(token)`,
  `stopPreview(token)`, `restartPreview(token)`, `previewBuild(token, buildId)`.
- New proxy routes: `app/api/preview/route.ts` (GET), `app/api/preview/stop/route.ts` (POST),
  `app/api/preview/restart/route.ts` (POST), `app/api/jobs/build/[id]/preview/route.ts` (POST) —
  same shape as every existing proxy route in this app.
- Wired into `studio-chat.tsx`: a new `previewVersion` counter state, bumped after every successful
  edit response; `<StudioPreview buildId={buildId} previewVersion={previewVersion} />` rendered at
  the top of the workspace column (above `StudioWorkspace`) inside the existing `.studio-grid` —
  the same lifted-state shape R-481's later tab bar will reuse, not a throwaway wiring.

**Implementation note**: `eslint-plugin-react-hooks`'s `set-state-in-effect` rule flagged a
`setState` call made synchronously and unconditionally at the top of the buildId/previewVersion
effect (the classic React docs "set loading, then fetch" pattern) - not because of anything
functionally wrong, but because this rule's own guard-clause exception (already used successfully
elsewhere in `studio-chat.tsx`'s turns-hydration effect, an early-return-then-bail pattern) does not
cover a `setState` call that is followed by further work in the same synchronous scope. Fixed by
moving the single combined `setPhase({starting: true, ...})` call to be the first statement inside
the effect's own async IIFE rather than before it - functionally identical, and it also motivated
consolidating `starting`/`elapsedMs`/`fetchError` into one `phase` state object so there is exactly
one `setState` call at the top of that continuation, not several cascading ones.
