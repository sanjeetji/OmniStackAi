# R-519: Template format + registry (Phase T, T-1)

**Phase:** Phase T (Template Marketplace)
**Status:** COMPLETED
**Started:** 2026-09-21
**Completed:** 2026-09-21

## Objective

Define what a template is, validate it strictly, list it, and let a signed-in user turn one into
their own project. The founder's model (2026-09-21):

- The **original template never changes** and is the same for every user.
- **"Use template"** creates a normal project owned by that user. It is a full copy of the
  template's code with its own git history, and it appears in their project list like any other
  project.
- The user customises **their copy only**: adding or removing features and changing behaviour.
  Template upgrades apply to new copies only, never silently to existing ones.

## Design

### Template format: `templates/catalog/<slug>/`

```
template.json   manifest (schema_version 1)
repo/           the complete golden source repository that gets copied
media/          optional cover and screenshots referenced by the manifest
```

Manifest fields (validated in `studio/templates.py`, documented in `templates/catalog/README.md`):
`schema_version` (1), `slug` (must equal the directory name), `name`, `version` (semver),
`category` (mobility | commerce | healthcare | education | real-estate | services | fintech |
content), `tagline`, `description`, `apps[]` ({id, name, kind: web|admin|pwa|api, path}),
`roles[]` ({id, name, description}), `entities[]`, `features[]`, `integrations[]`
({id, kind, provider, mock}), `demo_users[]` ({role, name, email, password}; role must be declared),
`stack[]`, optional `cover` / `screenshots[]` (must exist under the template dir).

Repo rules: every app `path` exists. An `api` app has a `migrations/` dir with ≥1 `.sql`. No
`.git`, `node_modules`, real `.env` files (`.env.example` is fine) or symlinks. Size and file-count
limits. **Digest** is `sha256` over the sorted (path, content-hash) list, so a project can prove
exactly which original it started from.

### Agent-engine (Python, stdlib only)

- `studio/templates.py`: `TemplateCatalog` (root = `OMNISTACKAI_TEMPLATE_CATALOG` or the repo's
  `templates/catalog`), `validate_template`, and `instantiate_template`. Instantiation copies
  `repo/` into the workspace, runs `git init`, commits "Template: <name> v<version>", and writes
  `state.json` with `kind: "template"` and `template: {slug, version, digest}`. It refuses a
  non-empty target. Invalid templates are never listed.
- Routes: `GET /api/templates`, `GET /api/templates/{slug}`,
  `POST /api/workspaces/{id}/from-template` `{slug}`.
- Guards that protect the copy: a prompt build or an IR edit on a `kind: "template"` workspace is
  refused with a clear message, because it would overwrite or ignore the template code. Template
  chat edits arrive with the code-edit agent (T-4).

### Control-plane (Go, no new dependency)

- New package `internal/templates`: `GET /templates` and `GET /templates/{slug}` (public catalogue
  reads, proxied), `POST /templates/{slug}/use` (auth), and `GET /projects/{id}/template` (auth,
  ownership).
- `use`: fetch the template → create the project (named after the template, in the caller's
  workspace) → agent-engine `from-template` → record the build result → insert a
  `project_templates` row. If any step fails, the project is deleted, so there are no orphans.
- Migration `000016_project_templates`: a separate table (project_id PK → projects ON DELETE
  CASCADE, slug, version, digest). **No existing project query changes.**

### Not in this task

Real templates (T-6+), console marketplace UI (T-3), multi-app preview/DB seeding (T-2), and chat
edits on template projects (T-4).
