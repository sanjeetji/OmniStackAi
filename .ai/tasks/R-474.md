# R-474: File browser in the console Studio — see what a build actually produced

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-18
**Completed:** 2026-09-18

## Objective

Continue Phase D of `R_&_D/OmniStackAI_Commercial_Platform_Kickoff_v1.md`. R-473 shipped a build
result panel that lists filenames as inert text; this task makes that list clickable so a user can
actually read the generated code, not just see that files exist. The agent-engine's Studio server
already has real, tested, path-safe read-only file access (`studio/files.py`, wired as
`GET /api/build/{id}/files` and `GET /api/build/{id}/file?path=...` since R-467) — this task bridges
those two existing endpoints through the authenticated control-plane, the same "generic proxy, no
new agent-engine code" shape R-472 established for the build endpoint itself.

## Design

- **`services/control-plane/internal/jobs`**: two new authenticated, read-only GET routes —
  `GET /jobs/build/{id}/files` and `GET /jobs/build/{id}/file?path=...` — proxying verbatim to the
  agent-engine's existing `GET /api/build/{id}/files` / `GET /api/build/{id}/file?path=...`. No
  credit debit (browsing already-generated files is not a billable model call). A shared
  `proxyGet` helper does the actual forwarding; `handleBuild`'s inline auth-error mapping is
  factored into a small `writeAuthError` helper so all three handlers share it instead of repeating
  the same `errors.Is(err, auth.ErrUnauthenticated)` block three times.
- **No agent-engine changes** — `studio/files.py` and its two existing routes are reused exactly as
  they are; R-467's path-safety guarantees (traversal-proof, secret-`.env`-excluded, binary-file-safe)
  carry over unchanged since nothing about them is touched.
- **`apps/console-web/lib/control-plane.ts`**: `BuildFileTreeResponse`/`BuildFileContentResponse`
  types (matching `studio/files.py`'s exact shapes) and `listBuildFiles(token, buildId)` /
  `readBuildFile(token, buildId, path)` client functions, following the existing `callControlPlane`
  pattern. `BuildJobResponse` gains a typed `id?: string` (already round-tripping today via the
  index signature; typing it lets the UI use it without a cast).
- **Two new proxy Route Handlers**: `app/api/jobs/build/[id]/files/route.ts` and
  `app/api/jobs/build/[id]/file/route.ts` — same session-cookie-gated, bearer-token-attached
  pattern as `app/api/jobs/build/route.ts`.
- **`studio-form.tsx`**: each filename in the result panel's file list becomes a button; clicking
  one fetches its content and renders it in a read-only `<pre>` viewer alongside the list (a
  binary file reports "binary file, not shown" rather than garbling raw bytes, matching
  `read_build_file`'s own `binary: true` signal).

## Known, honest limitation (not fixed by this task, not silently hidden)

The agent-engine's Studio server (`StudioBuildHistory`) is a single shared in-memory process with
no per-user scoping — this is unchanged from R-467 and is a pre-existing property of the Studio
server, not something this task introduces or worsens. Any authenticated console user who knows (or
guesses) a `build_id` can browse its files through this new proxy, the same way any local Studio
user already could before an authenticated frontend ever existed. Real per-user build isolation
requires the Studio server itself to become multi-tenant-aware - out of scope here, and worth
naming as a real gap before this ever leaves a single-operator/trusted-demo deployment.

## Explicitly out of scope for this task

- Live preview (running the generated app) — executes arbitrary generated code, a materially
  different trust/security posture than read-only file viewing; needs its own scoped decision.
- Editing files or triggering a follow-up build from the viewer (R-468's chat/edit flow) — separate
  task.
- Syntax highlighting in the viewer — a `<pre>` block is enough for v1; a highlighter is a UI-polish
  follow-up, not core functionality.
- Any change to `services/agent-engine` — its file-serving routes are reused exactly as they are.

## Acceptance Criteria

- [x] `GET /jobs/build/{id}/files` and `GET /jobs/build/{id}/file?path=...` require authentication
      (401 with no session) and otherwise proxy the agent-engine's response verbatim (status + body).
- [x] An unknown `build_id` returns the agent-engine's own 404, not a control-plane crash or a
      different status.
- [x] A path-traversal attempt (`../../etc/passwd`) is rejected by the existing agent-engine
      safety check and proxied through as the agent-engine's own 400 — this task adds no new
      traversal risk.
- [x] Clicking a file in the console's result panel shows real file content read from the real
      generated repo on disk.
- [x] A binary file reports "binary file, not shown" instead of corrupted output (`content.binary`
      guard in `FileBrowser`; not separately live-proved with an actual binary file this round, but
      the exact same `read_build_file` response shape R-467 already tests is what this proxy
      forwards unchanged).
- [x] `pnpm run typecheck`/`lint`/`build` and `go build`/`vet`/`test` all clean; `task verify` stays
      green.
