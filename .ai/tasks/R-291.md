# R-291 — Optimistic Subcollection Child Delete with Rollback

**Status:** in_progress
**Phase:** BASIC/MVP — Founder Stage 0
**Branch:** `main`
**Complexity:** L2 (deterministic codegen)

## Objective

R-290 made the top-level collection delete optimistic. R-291 completes the story for the subcollection
(master-detail) child lists in both the collection master-detail screen and the dedicated detail screen:
deleting a child row hides it immediately and rolls it back (row reappears + the existing error toast) if
the server rejects; a reconcile effect prunes ids once the subcollection refetch removes them. Safe on
the deduped mutation hooks (R-288) and the race-safe R-286 `useList<Child>By<Parent>` hook. The
detail-screen main-record delete already clears selection immediately, so it is out of scope.

## Requirement

In `nextjs.py`, add `_subcol_delete_names(s_var) -> (state, setter)` (`<s_var>Deleting` /
`set<S_var>Deleting`). In the subcollection child-delete handler loop (both `_collection_screen_page` and
`_detail_screen_page`, which emit byte-identical handler blocks), when `sub.can_delete`:

- Emit `const [<s_var>Deleting, set<S_var>Deleting] = useState<string[]>([]);` and a reconcile
  `useEffect(() => { set<S_var>Deleting((prev) => prev.filter((did) => (<s_var>.data ?? []).some((x: any)
  => String(x.id) === did))); }, [<s_var>.data]);` before the handler.
- In the handler: `set<S_var>Deleting((prev) => [...prev, String(id)]);` before `await remove<Child>(id)`;
  in `catch`, `set<S_var>Deleting((prev) => prev.filter((x) => x !== String(id)));` before `toast.error`.
- In the child row map (both sites), source becomes `(<s_var>.data ?? []).filter((child: any) =>
  !<s_var>Deleting.includes(String((child as any).id)))` when `sub.can_delete`, else `<s_var>.data`.

Both screens already import `useState`+`useEffect`. No hook/API-client/backend/IR change; deterministic;
description-only-stable.

## Acceptance criteria

1. Deletable subcollection emits the `<s_var>Deleting` state + reconcile effect on `[<s_var>.data]`.
2. Handler optimistic add before `await remove<Child>(id)`; catch rolls back before `toast.error`.
3. Child row map iterates the deleting-filtered list when deletable; non-deletable maps `<s_var>.data`.
4. Both render sites carry it; success path (refetch + success toast) preserved.
5. Non-deletable subcollections emit none; description-only IR changes byte-identical.
6. Focused + related subcollection tests + full offline gates + both demos pass.
