# R-232 — Customer project assembler (one IR → a customer-owned monorepo)

## Requirement

Assemble a complete customer project from one Application IR (Brief §6/§34/§35): select the framework
adapters implied by `project_strategy`, generate each target, place it under the customer monorepo
layout, and merge into a single `GeneratedProject` with root files. With the Git service, one IR
becomes one customer-owned monorepo repo. Deterministic and offline. Committed directly to `main`.
New IDs continue after the workbook backlog's R-010..R-219 (this is R-232).

## Acceptance criteria

- `default_registry()` returns an `AdapterRegistry` with the Next.js, Python, and Go adapters.
- `assemble_project(ir, registry=None)` selects targets from `project_strategy`
  (`web_strategy == nextjs` → `apps/web`; `backend_strategy` go/python → `services/api`; node backend
  and admin/mobile are skipped and documented as not-yet-assembled), generates each, re-paths its
  files under the monorepo layout, and returns one `GeneratedProject` (target `customer-monorepo`) plus
  a root `README.md` (lists the assembled apps) and root `.gitignore`.
- Safe, unique, deterministically ordered paths; pure function of the IR; standard-library only; no
  install/build/run/disk write.
- The assembled project materializes via the Git service into one customer-owned repo with a single
  commit (verified offline in a temp dir).
- `task verify` stays green.

## Design notes

- `codegen/assembler.py`: `default_registry()`, `assemble_project()`, `_prefixed()` helper (re-path a
  sub-project's files under a directory). Reuses `AdapterRegistry`, the three adapters, and
  `GeneratedProject`. The end-to-end test uses `git_service.create_repository`.

## Model and cost trace

Deterministic; no model call. No cloud key set; cloud_calls zero.
