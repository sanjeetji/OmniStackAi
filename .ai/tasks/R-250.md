# R-250 — Richer field validation (max_length + enum) into the schema and FastAPI models

## Requirement

Make the IR `Field.validation` tuple meaningful (Brief §9/§26/§27): a small deterministic rule syntax —
`max_length:<int>` and `enum:<a>|<b>|<c>` — threaded into the generated PostgreSQL schema and the
FastAPI Pydantic models. Unknown rules are ignored (forward-compatible). Go request-validation tags are
deferred (the schema already constrains Go writes at the DB). Additive, offline; example IRs unchanged
(feature exercised by constructed-IR tests). Committed directly to `main` (R-250).

## Acceptance criteria

- `parse_field_rules(field)` parses `max_length:<int>` and `enum:<a>|<b>|...`; unknown rules ignored;
  deterministic.
- Schema: a STRING field with `max_length` → `VARCHAR(n)` (else `TEXT`); an `enum` → a
  `CHECK (<col> IN ('a','b'))` appended after `NOT NULL`/`UNIQUE` (values single-quote-escaped); the
  `id` PK unaffected.
- Pydantic models: `max_length` (STRING/TEXT) → `Field(max_length=n)` (`Field(default=None,
  max_length=n)` when optional); `enum` → `Literal["a","b"]` type; imports added only when used; models
  parse as valid Python.
- No change when a field declares no rules; example IR outputs unchanged; nothing runs.
- Offline tests cover the parser, schema VARCHAR/CHECK, Pydantic Field/Literal, no-rules pass-through,
  and examples-unaffected.

## Design notes

- New `codegen/field_validation.py`: `FieldRules(max_length, enum)` + `parse_field_rules(field)`.
- `schema_sql._column_lines`: STRING+max_length → `VARCHAR(n)`; enum → `CHECK (...)` (local single-quote
  escaper); id branch unchanged.
- `backend_python._models_file`: apply `Field(...)`/`Literal[...]`; add `Field`/`Literal` imports only
  when used.
- Go models unchanged this task; export `parse_field_rules`/`FieldRules` from `codegen` if useful.

## Model and cost trace

Deterministic; no model call, no network, no DB connection. cloud_calls zero.
