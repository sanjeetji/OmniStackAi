# R-282 — Server-Side Boolean/Enum Field Filters on Top-Level LIST Endpoints

**Status:** done
**Phase:** BASIC/MVP — Founder Stage 0
**Branch:** `main`
**Complexity:** L3

## Objective

Add real server-side per-field equality filtering to the generated backends, following the exact pattern
of sorting (R-258) and search (R-261). A top-level LIST endpoint now accepts `?<field>=<value>` for each
**boolean** field and each **enum** field (fields with an `enum:a|b|c` validation rule), composed into
the SQL `WHERE` alongside the existing `q` keyword search. This is the backend capability that makes
R-278's client-side collection filters correct across pagination; wiring the frontend controls to it is a
follow-up (**R-283**). Scoped to `Op.LIST` (top-level lists); FK-scoped `Op.LIST_BY` subcollection queries
are unchanged. The founder chose the offline candidate and kept the available Groq key for later.

## Safety (whitelist discipline)

Column **identifiers** only ever come from validated IR field names (fixed strings in the generated
code); filter **values** are always parameterized (`$N` / `%s`), exactly like `q`/`limit`/`offset`. A
request can never inject a column name. This mirrors the R-258 sort whitelist.

## What changed

- **`field_validation.filter_fields(entity)`** — new shared helper returning `(field, kind)` for boolean
  and enum fields (excluding `id`); the single source of truth for both backends and OpenAPI, matching
  the frontend's boolean/enum filter selection.
- **`data_access` (Python)** — for a filterable entity, `_python_repository` emits a
  `_list_filters(q, <field>=None…)` helper and `list_`/`count_` with the filter kwargs; the WHERE is
  built dynamically (q clause + `col = %s` per set filter). Non-filterable entities are byte-identical.
- **`data_access` (Go)** — for a filterable entity, `_go_entity_store` emits a
  `<table>Filters(q string, filters map[string]string) (string, []any)` helper (bool → `v == "true"`,
  enum → `v`) with correct `$N` numbering, and `List`/`Count` take a `filters map[string]string`.
  Non-filterable entities are byte-identical.
- **`backend_python`** — the `Op.LIST` router branch declares typed filter query params
  (bool → `bool | None`, enum → `str | None`) and forwards them to `count_`/`list_`.
- **`backend_go`** — `parseFilters(r)` added to `handlers.go` (only when a filterable entity exists); the
  `Op.LIST` handler branch calls it and threads the map into the store calls.
- **`openapi`** — `render_openapi` documents each filter param on `Op.LIST` (boolean schema for bool,
  string + `enum` for enum).

## Acceptance criteria

1. `filter_fields` selects bool + enum, excludes `id`/plain.
2. Python: `list_item`/`count_item` gain `active`/`status` kwargs + `_list_filters`; conditions
   parameterized; router declares `active: bool | None` / `status: str | None` and forwards.
3. Go: `itemFilters` helper + `List`/`Count` `filters` map; `v == "true"` / `v`; `parseFilters` in
   `handlers.go`; handler passes filters.
4. OpenAPI `/items` GET documents `active` (boolean) and `status` (string enum new|used|sold).
5. Non-filterable project (`rideshare-favourites`) emits none of the filter plumbing (byte-identical).
6. `task verify` (new `test_field_filters_backend.py`), `task lint`, `task security:quick`, both
   `builder:demo`s pass.
