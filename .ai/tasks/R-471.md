# R-471: Fix dev-mode hydration bug + add full name to registration

**Phase:** MVP
**Status:** COMPLETED
**Started:** 2026-09-17
**Completed:** 2026-09-17

## Objective

Founder tried the real R-470 console in a browser and hit two problems: (1) registration silently
did nothing, and (2) the registration form is too bare (asked whether Name/Gender/Age would be
"helpful later"). This task fixes both and renumbers the kickoff doc's Phase C from R-471 to R-472
accordingly (this task is real, scoped work, not a footnote on R-470).

### Bug 1: registration silently did nothing (found via the founder's own live report)

`apps/console-web/next-dev.log` shows the exact mechanism: `⚠ Blocked cross-origin request to
Next.js dev resource /_next/hmr from "127.0.0.1"`, immediately followed by
`GET /register?email=...&password=... 200`. Next.js 16's dev server treats `127.0.0.1` and
`localhost` as distinct origins and blocks the former from loading its own hydration/HMR script as
a security default (`allowedDevOrigins`) — I had told the founder to open `http://127.0.0.1:4321`.
With no client-side JS hydrated, the `<form onSubmit>` handler never attached, so submitting the
form fell back to the browser's native default: a plain GET request with the fields serialized
into the URL query string, reloading the register page and doing nothing. This is exactly the fix
Next.js's own warning prescribes. Fixed in `next.config.ts` with `allowedDevOrigins: ["127.0.0.1",
"localhost"]`. Honestly noted: I cannot click a real browser button to re-confirm hydration now
works — this is the documented fix for the exact warning that was logged, verified by confirming
the warning no longer appears on a fresh request cycle, but the founder retrying registration in
their browser is the real confirmation.

### Feature: full name at registration

Founder asked whether Name/Gender/Age would help "later" and asked me to check and decide.
Decision, made explicit rather than silently picked: add **Name** (broadly useful — personalization,
addressing the user, later invoicing; the home page currently only has an email to show). **Do not
add Gender or Age** — neither serves any function anywhere in this product's actual roadmap
(credits, plans, a builder Studio), and collecting them would be pure unused PII with real privacy/
compliance liability (gender is special-category data under some privacy regimes) for zero
product benefit. If a real, specific reason for either surfaces later, that is its own decision to
make deliberately then, not a default to reach for now.
